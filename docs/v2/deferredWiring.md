# Отложенные замыслы (снято с 1.0.0 на этапе 3.4)

> Код удаляется — идея нет. Каждая секция фиксирует: что было задумано, почему
> снято с 1.0.0 и что нужно решить перед возвращением. Прецедент-обоснование
> правила — VibeIDE 2026-07-15: «мёртвые» файлы оказались носителями живых
> замыслов. Реализации ищутся в git до коммита удаления (`git log --diff-filter=D`).

## Расписание автосинхронизации (`syncSchedule`, `syncScheduleExtended`)

**Замысел.** Окно времени для автоматических триггеров: вне окна операции
копились в `schedule-deferred.json` и выполнялись при входе в активное окно.
Парсер поддерживал `hourly`, `daily HH:MM[,HH:MM…]`, `workhours 30m`,
`weekly mon 09:00` (`syncSchedulePlanner.ts`, чистый модуль с тестами);
персистентная очередь с дедупликацией пофайловых операций
(`syncScheduleDeferredStore.ts`); детектор перехода «вне окна → в окне»
(`syncScheduleTransition.ts`).

**Почему снято.** Расписание имеет смысл только для авто-действий, а модель
1.0.0 их запрещает: фон — детектор, действия — по команде (аудит B3). После
этапа 3.2 очередь всё равно не исполнялась сама — окно открывалось и лишь
предлагало кнопку, то есть настройка перестала управлять чем-либо, кроме
момента показа уведомления. `syncScheduleExtended` не была подключена никогда.

**Перед возвращением решить.** Расписание чего именно: детекторных проходов
(безобидно, можно вернуть как «интервалы проверки») или действий (противоречит
инварианту — потребует явного согласия уровня `tasks.allowFileMutations`).

## Тихие часы (`quietHours.*`, `autoSyncModeAdaptive.ts`)

**Замысел.** «check-only днём, full ночью»: внутри окна `quietHours`
эффективный режим повышался до `full` — «никто не работает, фоновая
синхронизация безопасна». Чистый модуль HH:MM-математики с переходом через
полночь, с тестами.

**Почему снято.** Спроектированное повышение режима без ведома пользователя —
ровно то, что аудит запретил (B9): «пока никто не смотрит» — не согласие.
Фактически апгрейд и не доезжал до исполнителя (эффективный режим повторно
читался из сырой настройки), то есть фича была мертва с рождения.

**Перед возвращением решить.** Возвращать не как повышение режима, а как
расписание *детектора* (реже проверять днём, чаще ночью) — тогда инвариант
не затрагивается.

## Дельта-синхронизация (`deltaSync`, `deltaThresholdKB`, `deltaSyncGate.ts`)

**Замысел (§8.2 роадмапа).** Экономия трафика на *скачивании*: rolling-hash
CDC (Rabin-Karp), дельта как список операций copy/insert, реконструкция новой
облачной версии из локального кэша старой + дельта-патча. Загрузка всегда
полная (провайдеры не умеют частичный PUT). В `deltaSyncGate.ts` были готовы
гейт по размеру, CDC-чанкинг и `deltaApplyFromCloud` (вызывался только из
тестов); в движке ветка заканчивалась пустым `if` (C24).

**Почему снято.** Фича не была реализована — настройки обещали то, чего код
не делал, а nls-описания не помечали её как эксперимент. Для 1.0.0 честнее
не обещать.

**Перед возвращением решить.** Где хранить кэш старых облачных версий (это
предпосылка алгоритма) и как дельта уживается с шифрованием и gzip: патчить
можно только plaintext, значит дельта требует локального plaintext-кэша.

## Правила авто-разрешения конфликтов (`conflictRules`)

**Замысел.** Массив `{ pattern: minimatch, strategy: keep-mine | take-theirs |
newer }`: конфликт по подходящему glob разрешается автоматически до показа
пользователю. В движке были `matchConflictRule` + `applyConflictRule`.

**Почему снято.** Настройка не была подключена (фабрика движка поле не
передавала — B14), а подключать «как есть» нельзя: `take-theirs` из фонового
тика молча перезаписывал бы локальный файл — прямое нарушение «ничего без
спроса».

**Перед возвращением решить.** Правило задаёт только **предлагаемое** действие
в UI разрешения конфликта (предвыбор в панели «Расхождения»), не автоматику.

## Окончания строк (`lineEnding`)

**Замысел.** Режимы `lf | crlf | preserve` для канонизации перед хэшем, чтобы
CRLF-машины и LF-машины видели одинаковый хэш; подсказка при `.editorconfig`
с `end_of_line = crlf`.

**Почему снято.** Канон фактически всегда LF: `stripSyncignoreBlocks`
безусловно схлопывал результат `crlf`-нормализации обратно в LF (C25), значит
режимы `crlf`/`preserve` не работали, а подсказка «поставьте crlf, чтобы хэш
совпадал» вводила в заблуждение. Ветка preserve-конфликта была достижима
только для CR-only файлов.

**Перед возвращением решить.** Нужен ли он вообще: канонический LF-хэш уже
делает хэши машин совпадающими независимо от локальных переводов строк.
Внутренний `LineEndingMode` в движке сохранён (тестируется), удалена
пользовательская настройка и подсказка.

## Единый диспетчер тиков движка (`scheduledJobsDispatcher.ts`)

**Замысел.** Свести три независимых планнера (`syncTickPlanner`,
`backupVerifyScheduler`, `autoPauseTickPlanner`) в один упорядоченный список
действий на тик + расчёт следующей побудки, чтобы polling-петля движка стала
декларативной: «что делать в момент T?» → список.

**Почему снято.** Скелет «wiring deferred» (коммит 8beb347): из продакшена его
не вызывал никто, единственный потребитель — собственный тест. Из трёх
агрегируемых планнеров один (`syncTickPlanner`) удалён вместе с расписанием
синка, ради которого агрегатор и затевался. Живые планнеры
(`backupVerifyScheduler`, `autoPauseTickPlanner`) остаются в кодовой базе.

**Перед возвращением решить.** Нужен ли агрегатор вообще при модели
«фон = детектор»: расписание детекторных проходов может снова сделать его
полезным, но тогда его вход — детекторные тики, не sync-действия.

## Bulk Pull (`vscodesync.bulkPullSelected`)

**Замысел.** QuickPick со списком cloud-newer файлов, множественный выбор,
скачивание выбранных с прогрессом.

**Почему снято.** Панель «Расхождения» (этап 3.5) делает то же самое полнее:
группировка, направления, причины, конфликты. Две точки входа для одного
действия — расход палитры (F12).
