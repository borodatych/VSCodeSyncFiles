## Зачем

Структура проекта на работе и дома может отличаться. Сегодня файл в синке
идентифицируется относительным путём: `ManifestFile.path` — одновременно и
идентичность, и раскладка, и адрес блоба. Единственная уступка различиям машин —
`pathMapping` (машина → корень), структура ниже корня обязана совпадать.

Нужно: стабильная логическая идентичность файла (**линковочное имя**), к которой
каждая машина привязывает **свой** локальный путь; перепривязка при переносе;
детекция дубликатов при добавлении; выбор «принять структуру отправителя или
положить по-своему» при скачивании.

Инвариант продукта не меняется: **данные двигает пользователь** — bind/rebind
всегда чистые метаданные, перемещение содержимого только явной командой.

## Модель данных

### Облачный манифест (`.vscodesync-workspace.json`), schemaVersion остаётся 1

`ManifestFile.path` **не меняется**: канонический (source) относительный путь,
ключ merge и адрес блоба `VSCodeSyncFiles/<wsId>/<path>[.gz]`. `_meta.json` не
меняется вовсе. Три новых необязательных поля строки:

- `linkId?: string` — 16 hex, стабильная идентичность, переживает канонические
  переименования. Новые строки: `randomBytes(8).hex`. Легаси-строки — ленивый
  **детерминированный** бэкфилл `sha256(path + "\0" + addedAt).slice(0, 16)` при
  любой уже происходящей записи манифеста. Бэкфилл **не бампает** `version`:
  сходимость даёт детерминизм (две машины запишут одно и то же), а не Lamport.
- `linkName?: string` — человеческая метка («линковочное имя»), не ключ, коллизии
  допустимы; дефолт `basename(path)`; все пикеры дизамбигуируют каноническим путём.
- `bindings?: Record<machineId, { path: string; boundAt: string }>` — «на машине M
  этот логический файл лежит по пути path». Ключ присутствует, только если путь
  отличается от канонического. **Отвязка = запись своего ключа со значением
  `path === каноническому`, никогда не удаление ключа** (удаление + union
  воскрешает ключ из старых копий). Ключи машин, выпиленных из `machines[]`,
  чистятся в точке purge tombstone-ов (`manifestStore`).

Дисциплина версий: изменение `linkName`/`bindings` **пользовательским действием**
бампает `version` строки `Math.max(nextManifestVersion, prev.version + 1)` — иначе
поле молча проигрывает каждый 412-merge. Исключение — детерминированный бэкфилл
`linkId` (см. выше).

### Merge (`manifestMerger.mergeManifestFiles`)

Победитель строки — по-прежнему больший `version` (tie-break `addedAt`; при полном
равенстве и различающихся identity-полях — детерминированный лексикографический
tie-break вместо порядко-зависимого). Поверх победителя:

- `bindings` — **по-ключевой union обеих карт с победой более свежего `boundAt`**
  (не победа строки-победителя целиком): закрывает потерю привязки при гонке
  rebind ↔ несвязанная правка строки (soft-lock, linkName). Паттерн уже есть в
  кодовой базе — `mergeMachinesPreferNewer`.
- `linkId` — графт: победитель без `linkId`, проигравший с ним → скопировать
  (спасает идентичность после v1-repair, переписавшего `addedAt`).

Обязательны property-тесты (идемпотентность, коммутативность, сходимость при
произвольных перестановках 412-retry) + симуляция «v1-merge × v2-merge» на одной
паре манифестов.

### Папочные правила (`folderBindings`) — работа `promed/**` ↔ дом `php/**`

Запрос владельца 2026-08-11: папка может называться по-разному на машинах при
одинаковой структуре внутри. N по-файловых привязок недостаточно — правило
обязано действовать и на **будущие** файлы. Поэтому на уровне манифеста:

```
folderBindings?: Record<machineId, Record<каноничныйПрефикс, { path: локальныйПрефикс; boundAt }>>
```

- Merge — по-(машина, префикс) LWW на `boundAt` (`mergeFolderBindings`), Lamport
  не участвует; prune правил выпиленных машин — в той же точке гигиены записи.
- `TrackedFile.manifestPath` остаётся рабочей лошадкой: sync-потоки правил не
  читают. Правило применяется в трёх точках рождения записи:
  1. **bindLocalFolder** — пишет правило, перепривязывает застрявшие на
     каноническом размещении строки (файл реально лежит под локальным
     префиксом), затем штатный adopt;
  2. **adopt** — новый облачный `promed/api/new.php` регистрируется локально
     как `php/api/new.php` + `manifestPath` (`localPathForCanonicalKey`);
  3. **addFiles** — новый локальный файл под `php/` получает канонический ключ
     `promed/…` (`canonicalKeyForLocalPath`).
- Файловая привязка сильнее папочной; из папочных выигрывает самый длинный
  префикс. Резолвер — чистый `src/core/folderBindings.ts`.

### Локальный конфиг (`.vscode/vscodesync.json`)

`TrackedFile` получает:

- `manifestPath?: string` — канонический ключ строки манифеста / `_meta.files`.
  Отсутствует ⇒ семантически равен `localPath` — **каждый существующий конфиг
  валиден без миграции**. Записывается только при создании привязки.
- `linkId?: string` — кэш идентичности (пере-ассоциация после чужих rename).

`localPath` сохраняет семантику «путь на ЭТОЙ машине»; `cloudPath` остаётся
денормализованным кэшем от канонического ключа.

**Единый хелпер `manifestKeyOf(f) = f.manifestPath ?? f.localPath`**
(`src/core/trackedPathResolver.ts`). Все точки, ключующие манифест / `_meta` /
блоб по `localPath`, переводятся на него; гейт-тест поимённо перечисляет
непереведённые места (прецедент C13 — такие рефакторинги без гейта текут).
Известная дыра до фичи: `reportTrackingDrift` строит `trackedPaths` из
`f.localPath` (`syncEngine.ts:2852`) — для привязанного файла это вечный ложный
adopt-тост.

### Новый статус `missing_local`

`TrackedSyncStatus` получает `"missing_local"` (файл трекается, на диске
отсутствует). Сегодня это состояние прячется в `localHash: ""` + `cloud_newer`, а
декорация показывает «✓ synced» (баг `fileDecorations.ts:104`). С привязками
отсутствие на диске — частое честное состояние: своя декорация, свой
`contextValue` ноды (для действий «Привязать…» / «Перепривязать…» / «Скачать»).

## Потоки (5 сценариев владельца)

1. **Имя при отправке.** Одиночное добавление — InputBox с префиллом basename;
   массовое — авто-basename без вопросов. Переименование метки —
   `vscodesync.renameLinkName` (правка строки, bump version). Канон структуры
   фиксируется как сегодня — `path` добавляющей машины.
2. **Привязка на машине B** — `vscodesync.bindLocalFile` (палитра; нода дерева;
   row-action панели «Расхождения» на «есть в облаке, нет локально»). Пикер
   записей поднимает совпадающие по hash/basename наверх с пометкой «совпадает
   содержимое»; превью «синхронны / появится расхождение»; гарды: локальный путь
   уже трекается → ошибка; запись уже привязана здесь → предложить замену;
   tombstone-строка → отказ «файл удалён с облака» + «добавить как новый»
   (анти-воскрешение); вне sync root → отказ со ссылкой на Path Mapping.
   Запись: `TrackedFile{localPath, manifestPath, linkId}` +
   `bindings[machineId] = {path, boundAt: now}` + bump version → штатный
   `putManifest` (412-merge цикл). Контент не двигается.
3. **Перенос/переименование.** Живой rename → модалка: «Переименовать в облаке
   (для всех)» (существующий `renameTrackedFile` + перенос `linkId` и `bindings`
   на новую строку) / «Только здесь (перепривязать)» (`rebindTrackedFile`: только
   `localPath` + `bindings[me]`, ни блобов, ни tombstone) / «Отвязать здесь».
   Case-only rename → рекомендация «только здесь», на облачном — предупреждение
   (OneDrive регистронезависим). Промпт удаления получает 4-й пункт «Файл переехал
   — перепривязать…». Реплей чужого канонического rename: привязанная машина —
   молча (обновляются `manifestPath`/`cloudPath`); непривязанная — молчаливая
   **локальная** пере-ассоциация (`manifestPath = новый канон`, синк не рвётся) +
   тост «Принять новую структуру? [Переместить у меня / Оставить мою]»;
   облачная подсказка `bindings[B]` пишется **попутно со следующим штатным PUT
   манифеста**, не отдельным авто-PUT (иначе N машин × 412-шторм и размывание
   «данные двигает пользователь»).
4. **Дедуп при добавлении.** Чистый планировщик `planAddDuplicates(candidates,
   manifest, meta)`: совпадение по контент-хэшу (Map по hash, O(N+M)) и по имени
   (basename/linkName); tombstone пропускаются. Модалка «Привязать к существующей /
   Добавить как новую / Пропустить»; массовое добавление — один canPickMany
   QuickPick вместо N модалок. Детекция только предлагает, никогда не принуждает.
5. **Pull с выбором размещения.** Одиночный pull отсутствующего файла — QuickPick
   «Как у отправителя: <канон>» (дефолт) / «Выбрать папку и имя…» / «Привязать к
   существующему файлу…» (bind без скачивания). Массовый pull — один батч-вопрос
   «Принять структуру отправителя для N файлов? [Принять / Разобрать по одному /
   Отмена]». Первичный attach воркспейса — честная модалка «файлы будут разложены
   по структуре отправителя; отдельные можно перепривязать после». Фоновый adopt
   не меняется — фон молчалив.

UI-обвязка: бейдж «⇄ <канонический путь>» на привязанных нодах дерева — без него
непонятно, почему «переименовать в облаке» спрашивает про все машины.

## Конкурентность

Всё едет штатным конвейером `putManifest` (validate → guard → PUT `ifMatch` → 412
→ re-download + merge + retry ≤3). Новых облачных объектов нет. Разборы гонок:

- **Два rebind одной строки с разных машин** — дизъюнктные ключи `bindings`,
  union сохраняет оба; общий ключ (одна машина из двух мест) — свежий `boundAt`.
- **v1-машина выполняет merge** (union-а нет) — row-LWW роняет ключ проигравшего →
  **самолечение**: на пользовательском проходе загрузки контекста, если
  `manifestPath ≠ localPath`, а `bindings[me].path ≠ localPath` — машина
  пере-утверждает свою привязку (bump version). Локальный конфиг авторитетен для
  собственной привязки; облачная копия — подсказка остальным. Rate-limit: не чаще
  раза за сессию на воркспейс (иначе две разошедшиеся машины пинг-понгуют PUT-ами).
- **Bind vs delete** — обе стороны бампают version, выигрывает большая; удаление
  победило → штатный prune-warning (диск цел); привязка победила при удалённом
  блобе → детектор показывает push и спрашивает («молчаливый re-push недопустим»).
- **Bind vs canonical rename** — tombstone новее → перенос привязки на новую
  строку / самолечение после `renamedFrom`-пере-ассоциации; bind новее → два живых
  носителя одного `linkId` → диагностика дубликата + one-click repair (tombstone
  старой, слияние её `bindings` в новую).
- **Mass-change guard** — бэкфилл и привязки его не триггерят (считает только
  tombstone); чисто метаданный diff классифицируется как metadata-only и не
  показывает drift-тостов соседям.

## Совместимость и миграция

- `schemaVersion` остаётся 1 (политика: optional-поля без bump). Проверено по
  v1-коду: merge копирует строки спредом, правки спредят prev, валидация проверяет
  только известные поля — v1-машины **не теряют и не отвергают** новые поля.
- v1-машина в привязанном воркспейсе — когерентный деградированный режим: видит
  только каноническую структуру, данные не портит.
- v1-«дропперы» строк: `renameTrackedFile` (новая строка с нуля — пере-ассоциация
  по `renamedFrom` первой v2-машиной) и repair-планировщики (пересборка строк —
  `linkId` восстанавливается детерминированным бэкфиллом, пока жив `addedAt`;
  `bindings` — самолечением). Repair, сбросивший `addedAt`, меняет `linkId`
  необратимо — принято, закрыто графтом linkId в merge.
- **Даунгрейд-хазард (задокументировать!):** v1-движок на машине, где
  `manifestPath ≠ localPath`, ключует по `localPath` → задвоение блоба под
  привязанным путём. Митигация: health-check-детекция пар «один hash — два пути» с
  предложением объединить + строка в доках «привязки требуют версии ≥ X на всех
  машинах воркспейса».
- Офлайн дольше окна purge (30 дн) с привязкой на переименованной строке →
  `renamedFrom` вычищен → adopt как нового файла + штатный prune-warning,
  перепривязка вручную (детекция дубликатов по hash сама предложит «это
  переименование?»).

## Крайние случаи

- Один контент в двух живых строках — допустимо (независимые логические файлы);
  один локальный файл не может быть привязан к двум строкам (гард по `localPath`).
- Привязка `.gitignore`-нутого файла — **разрешена без предупреждений** (целевой
  сценарий: `.env` и прочие негитуемые). Предупреждение — только при попадании под
  собственные ignore-шаблоны расширения («авто-детектор будет пропускать»).
- Файл вне sync root — отказ (traversal-гарды `pathMapping.ts`); ограничение
  «pathMapping только поддиректория workspace» в этой фиче не расширяется.
- Кросс-воркспейсная привязка — не поддерживается; перенос между воркспейсами —
  существующий move (remove + add, новый `linkId`). Дедуп сканирует только целевой
  воркспейс.
- Привязка к несуществующему файлу — запрещена (пикер выбирает существующие);
  «файл появится вот здесь» покрывается выбором места при pull.
- `registerFileLifecycleEvents` ищет по `f.localPath === rel` — для привязанных
  файлов обязан идти через тот же резолвер, иначе rename/delete-промпты не
  сработают.

   `vscodesync.renameLinkName`. Отступления: metadata-only классификация
   mass-change guard не понадобилась — guard уже считает только tombstone-ы;
   ремонт дубликатов surface-ится через health check (сообщение), запуск
   ремонта — этап полировки, функция готова и покрыта тестами.

Каждый этап самостоятельно ценен и сокращает окно смешанных версий.

- **Дерево папок** (`plan/planFileTree.ts`) — группировка по локальному
  размещению, схлопывание цепочек одиночных папок, бейдж `⇄ канон` один раз на
  папке и только когда всё поддерево согласовано (смешанное — без бейджа, он
  соврал бы про часть файлов). Настройка `vscodesync.tree.groupFilesByFolder`
  возвращает плоский список.
- **Отправка с обрезкой префикса** (`plan/planCanonicalRoot.ts`) — при
  добавлении одной папки предлагается «как есть» и каждый срез начала пути;
  выбранный вариант уходит в `addFiles({ canonicalRoot })`, который ключует
  файлы под новым корнем и записывает папочное правило этой машины.
- **Приём папки** (`plan/planFolderIntake.ts` + `ui/folderIntakePrompt.ts`) —
  при подключении воркспейса каждая верхнеуровневая облачная папка
  спрашивается: «Взять как есть» / «Положить в свою папку…». Целевая папка
  может не существовать (`bindLocalFolder({ localDirRel })`) — правило решает,
  куда попадут будущие файлы. Перед записью — предпросмотр «облако → сюда»,
  счётчик совпавшей структуры и список коллизий: файлы, уже лежащие на месте,
  не перезаписываются, а расходятся в панель.
- **Scope** (`syncScope.ts`) — `ActiveWorkspaceEntry.syncScopes`, пер-машинный
  список канонических префиксов. Пустой список = весь воркспейс (конфиги до
  фичи валидны). Фильтр стоит и в adopt, и в reportTrackingDrift — иначе чужая
  папка вечно висела бы «нет на диске». Снятие папки убирает её строки из
  локального трекинга, байты на диске не трогает; в облаке остаётся всё.

Инвариант «данные двигает пользователь» соблюдён: все три потока пишут только
метаданные, файлы перемещаются отдельной явной командой.
