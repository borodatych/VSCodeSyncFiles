# Правка канонических путей — редактируемая структура воркспейса

> Согласовано 2026-08-12 (владелец: «да» на план). Дизайн выбран из трёх
> конкурирующих (журнал переездов / минимальный батч-Lamport / UX-first
> Canonical Path Editor) панелью из трёх судей (сходимость / миграция / UX):
> победил UX-first (8.6 / 8 / 8.5) с графтом батч-инварианта единого
> Lamport-version из минимального дизайна и 14 обязательными доработками из
> судейских вердиктов. Разведка кода — 6 агентов, материалы в сессии.

## Зачем

Link Bindings отвязали идентичность файла от пути (`linkId`), но канонический
путь — ключ манифеста — оставался «структурой машины-отправителя», менять его
можно было только одиночным rename с диска. Владельцу нужно править структуру
**самого воркспейса**: переименовать любой узел (файл, папку, корень) прямо в
облачном дереве, чтобы дочерние пути перестроились, привязки машин не порвались,
а засев второй машины шёл по отредактированным путям.

Это даёт второй способ засева: залил с машины A → поправил пути в воркспейсе →
машина B при подключении раскладывает файлы уже по новой структуре.

## Модель: ноль новых полей

Wire-формат не меняется, `schemaVersion` остаётся 1. Переезд ключа — уже
существующая пара: **tombstone старой строки + строка-наследник** на новом пути
с `renamedFrom`/`renamedAt` и унаследованными `linkId`/`linkName`/`bindings`.
Клиенты 1.1.x–1.2.0 реплеят каждую пару своим существующим кодом.

Три несущих правила записи (`src/core/canonicalRename.ts`):

- **Батч-инвариант.** Все строки одного батча — tombstone-ы и наследники —
  несут ОДИН Lamport-version (`max(next, max(затронутых)+1)`) и один timestamp.
  Атомарность закодирована в форме данных: row-LWW merge (даже у старого
  клиента и на третьей машине) решает судьбу всей папки одинаково — папка
  не «рвётся» пофайлово между двумя конкурирующими переездами.
- **Материализация идентичности.** Легаси-строка без `linkId` живёт на
  детерминированном бэкфилле `sha256(path + addedAt)` — он зависит от пути и
  после переезда разошёлся бы. Rename пишет id явно в ОБЕ строки пары.
- **Наследник строится с нуля**, не спредом поверх строки на целевом пути —
  спред наследовал `removedAt` припаркованного tombstone (живой rename рождал
  мёртвую строку; баг существовал в одиночном rename).

Сходимость конкурентных переездов: проигравший батч оставляет наследников с
теми же `linkId` — дубликаты схлопывает детерминированный
`repairDuplicateLinkIds` (младший носитель выживает), который теперь едет в
каждом 412-merge (`manifestStore.put`). Property-тесты
(`canonicalRenameConvergence.test.ts`): 50 сидов случайных батчей × все порядки
merge × вырожденное равенство version/timestamp → одна живая структура.

## Порядок облачной операции

`io/canonicalRelocation.ts`, каждый шаг идемпотентен (повтор запроса доводит
прерванную работу):

1. **Блобы** переезжают на новые ключи. Быстрый путь — нативный
   `provider.moveFile` (метаданные, без перекачки), если категория хэширования
   не меняется; иначе транскод: download → decode → **пересчёт хэша под НОВЫМ
   ключом** (текст↔бинарь решается расширением) → encode → upload. `_meta`
   строка следует с новым hash/etag; verbatim-перенос был багом — хэш,
   который не воспроизведёт ни одна машина.
2. **История** `.history/<путь>/` следует за файлом (best-effort).
3. **ОДИН putManifest**: все пары + миграция `folderBindings` (правило машины
   переезжает на новый префикс со свежим `boundAt`, старый ключ
   **нейтрализуется** identity-записью — удаление воскресло бы union-merge-ем,
   а живое старое правило однажды подхватило бы новый файл под старым
   префиксом).
4. **PUT `_meta`** с перенесёнными строками.
5. **Удаление старых блобов — строго последним**: обрыв может оставить
   сироту-копию (возобновляемо, GC-able), но никогда — манифест, указывающий
   на удалённые байты. (Старый rename удалял блоб ДО putManifest.)
6. Локальные строки следуют **по ключу**: `manifestPath` переезжает,
   `localPath` (байты) не трогается; `syncScopes` машины ремапятся по
   префиксным ходам.

## Реплей у остальных машин

Семантика прежняя (договорённость Link Bindings): байты на диске → переезжает
только ключ; байтов нет → строка следует размещению нового ключа
(`placementOf`). Новое:

- **Фаза linkId-спаривания** в `planTrackingDiff`: `renamedFrom` одношаговый и
  вычищается через 30 дней — машина из долгого офлайна (или проспавшая цепочку
  a→b→c) спаривает «ушедший ключ ↔ пришедшая строка» по идентичности и
  получает переезд, а не prune+adopt-дубликат. Пара строится только при
  однозначности с обеих сторон. Кэш `TrackedFile.linkId` заполняется при
  каждом adopt/track (раньше — только при bind).
- **Один агрегированный тост на операцию** (`onCanonicalRenamesReplayed`):
  «папка X → Y (N файлов), пути обновлены, локальные файлы не тронуты» с
  кнопкой «Переместить у меня» — батч `workspace.fs.rename` с прогрессом и
  отменой. Общий префикс выводится чистым `inferCommonPrefixMove`.
- **Проигрыш конкурентного переезда виден** (`onCanonicalRenameOverridden`):
  после 412-merge писатель сверяет своих наследников с итоговым манифестом и
  показывает «переиграно более свежей правкой» — молчаливая потеря интента
  запрещена.

## UX: три входа в один поток

Все входы собирают запросы (`file` | `prefix`) и идут через
`planCanonicalRename` (композиция правок сессии, валидация, коллизии,
предупреждения) → одно модальное превью → `renameCanonicalKeys` с прогрессом:

1. **Команды дерева** — «Изменить путь в облаке…» (файл), «Переименовать
   облачную папку…» (папка/корень; схлопнутая цепочка `a/b/c` правится целой
   строкой).
2. **DnD внутри воркспейса** — файл/папка на папку или узел воркспейса =
   канонический переезд (раньше папки не тащились, невалидный drop молчал).
   Перенос между воркспейсами остаётся прежним remove+add.
3. **Массовый редактор** — «Редактировать пути воркспейса…» открывает буфер
   «строка = файл» (мультикурсор, regex-замены), «Применить правки путей»
   сводит диф в один батч. Строки соответствуют файлам по позиции.

Предупреждения превью: различие только в регистре (OneDrive/GDrive
регистронезависимы); **смена категории текст↔бинарь** — не только пересчёт
хэша: нормализация CRLF отключается, машины с другими переводами строк увидят
реальное расхождение содержимого; цель на tombstone («путь освободился»).

Обвязка: канон-режим дерева («локальное размещение ⇄ канонические пути»,
кнопка на панели) — правка структуры видна в том пространстве, где живёт;
прерванный батч персистится в `workspaceState` («Возобновить перенос», плюс
напоминание при старте); «Отменить переименование» — инверсный батч той же
машинерией (пока живы 30-дневные крошки).

## Засев по путям воркспейса (сценарий владельца)

1. Машина A заливает файлы (канон = её структура или выбранный canonicalRoot).
2. Пути правятся в облачном дереве с любой машины — байты нигде не двигаются,
   у правившей машины строки становятся «привязанными» (localPath ≠ канон).
3. Машина B подключается: intake-промпт «куда положить папку» теперь идёт
   **до** первого adopt/pull (`beforeInitialAdopt`) — правило размещения
   управляет и уже существующими файлами; adopt кладёт строки по
   `placementOf(отредактированный канон)`, forcePull скачивает байты туда.
4. После засева обеих сторон правки путей не дают конфликтов содержимого by
   construction: base=`_meta.hash` пересчитан под новым ключом, обе машины
   хэшируют те же байты под тем же ключом.
5. Отвязка (`untrackFileLocal`) пишет канон назад в `bindings[me]` (конвенция
   unbind; раньше привязка оставалась «врать» в облаке) — повторный засев идёт
   по текущим путям воркспейса.

## Совместимость

- Новых полей нет — манифест после любого переезда валиден для 1.1.x–1.2.0 без
  оговорок; старый клиент видит папочный батч как N одношаговых `renamedFrom`
  и реплеит их существующим кодом (N тостов вместо одного — косметика).
- `rebuildManifestFilesFromTracked` нумерует строки от high-water mark
  (`ActiveWorkspaceEntry.manifestVersionHighWater`, монотонный) — rebuild после
  потери облачного манифеста больше не проигрывает merge уцелевшим старым
  копиям (со сброса к `i+1` это была мина под фичей).
- Гарды rename-осведомлённы: tombstone с живым наследником (по `renamedFrom`
  или `linkId`) не считается удалением ни в mass-change guard, ни в
  предупреждении «файлы будут потеряны».
- 1.0.x-парк: прежний задокументированный даунгрейд-хазард (ключевание по
  `localPath`) массовые переезды усиливают — обновлять парк целиком.
