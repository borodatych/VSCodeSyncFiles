## [архитектура] UI-refresh chain после команд: три отдельных задержки

**Контекст:** жалоба пользователя «после первого Push All картина файлов не обновляется, после второго — обновляется». При расследовании выяснилось, что технически бага нет — `vscodesync.json` уже на диске свежий к моменту возврата из `engine.pushAll()`. Видимая «задержка» — это сумма трёх независимых факторов в UI-цепочке refresh, каждый со своими async-границами.

**Суть:** между «engine закончил» и «значок ✓ на месте» есть ТРИ слоя:

1. **Batched cfg writes в engine.** `syncEngine.ts:400-545` — внутри `withBatchedCfgWrites` все `persistMutatedCfg(c)` НЕ пишут на диск, только ставят `_batchCfgDirty = true`. Реальный `saveCfg` дёргается ОДИН раз в `finally` обёртки. К моменту `await engine.pushAll()` → диск уже свежий (правильно).

2. **Tree refresh debounced на 150 мс.** `workspacesTree.ts:187-195`:
   ```ts
   refresh(): void {
     if (this.refreshTimer !== undefined) clearTimeout(this.refreshTimer);
     this.refreshTimer = setTimeout(() => this._onDidChange.fire(undefined), 150);
   }
   ```
   Каждый новый `refresh()` сбрасывает таймер. Если в этом окне приходит ещё refresh — отсчёт начинается заново. Watch poller-tick / другие источники могут продлевать окно.

3. **File decoration provider — асинхронный с recomputation хешa.** `fileDecorations.ts:58-115`. На каждый файл provider делает: `await WorkspaceConfigManager.load()` (5–50 ms) + `await computeHash(uri.fsPath)` (10–500 ms на средний файл). На workspace из 24 файлов — 24 параллельные async-цепочки. Каждый новый `fileDecorations.refresh()` (= `emitter.fire(undefined)`) cancel'ит pending promises (через `token.isCancellationRequested` на стр.76) и запустит новые. Если refresh'ы идут чаще, чем successfully завершается provider — значки висят в неопределённом состоянии.

**Кэша в `WorkspaceConfigManager.load()` нет** (`workspaceConfigManager.ts:37-53` — каждый вызов читает с диска). Это правильно: позволяет mгновенно видеть свежий json после `saveCfg`.

**Применение:**

- Если пользователь жалуется на «UI не обновляется» после команды — сначала проверять, какой именно индикатор (tree node colour / file decoration significk / cloud icon tint). Это разные подсистемы, разные задержки.
- Если жалоба про **file decoration** (`✓` / `↑` / `↓` / `⚠` рядом с именами файлов): помнить про async hash recompute. На больших workspace до 1-2 секунд после refresh.
- Если жалоба про **tree** (цвет workspace, статус): помнить про 150 мс debounce.
- Прежде чем чинить, попросить пользователя подождать 2-3 сек после команды без действий. Если за это время картина обновилась — это асинхронная природа provider'а, не баг.
- Не «оптимизировать» через убирание debounce — он защищает от refresh-storm при многократных событиях (file watcher + scheduled poller + manual refresh могут срабатывать одновременно).
- Если реально нужно ускорить — кэшировать `computeHash` результаты в decoration provider (~1 сек TTL); сейчас этого нет.

## [архитектура] Логгер decoupled от vscode

**Контекст:** при создании centralised logger через `OutputChannel` и импорте его из `src/utils/log.ts` сборка CLI падала с `Could not resolve "vscode"` — CLI бандл (`cli/src/main.ts`) транзитивно тянул `log.ts` через провайдеры (yandexDiskProvider).

**Суть:** `src/utils/log.ts` НЕ должен импортировать `vscode`. Базовый logger хранит абстрактный `LogSink` с no-op default; VS Code-обвязка живёт в отдельном `src/utils/logVscode.ts` и регистрируется при `activate(...)` через `setLogSink`. CLI и тесты получают тихий no-op без падения.

**Применение:** любой shared utility, который импортирует `vscode`, не должен использоваться из общего кода поверх провайдеров; либо decoupling через инъекцию, либо отдельный файл-обвязка.

## [баг] Lint flow-narrowing считает мутируемые-извне поля недостижимыми

**Контекст:** `webhookTunnel.ts:69` — поле `disposed: boolean` устанавливалось извне (`dispose()`), но проверка `if (state.disposed) return` внутри `connect()` после `if (state.disposed) return` в начале функции трактовалась eslint как «всегда falsy».

**Суть:** typescript-eslint flow-analyser не учитывает мутации через side-effect. Чтение `state.disposed` напрямую сужается до literal `false` после первой проверки. Решение — спрятать чтение за функцию-геттер: `function isDisposed(s: RelayState): boolean { return (s as { disposed: boolean }).disposed; }`. Это делает чтение прозрачным для лента и сохраняет валидную проверку.

**Применение:** любые поля состояния, мутируемые из внешнего scope (timer-callback, dispose-callback, web event), читать через функцию-обёртку с явной типовой обвязкой.

## [vscode] vscode.lm не в @types/vscode для engines.vscode ^1.80

**Контекст:** компиляция `aiMerge.ts` проходит, но lint выдаёт ~30 ошибок `no-unsafe-*` на `vscode.lm.selectChatModels` и `vscode.LanguageModelChatMessage`.

**Суть:** в `@types/vscode` соответствующего минимального engine `^1.80` API нет; рантайм его экспонирует на 1.90+. Решение — type-shim в файле использования: declare local `interface LmApi { ... }` + `getLm(): LmApi | null` через `vscode as unknown as VscodeWithLm`. Lint не трогает, рантайм работает на поддержанных версиях.

**Применение:** для feature-gated VS Code API из новых версий — типизировать локально, не поднимать минимальный `engines.vscode` ради типа (это отрезает аудиторию).

## [баг] Git stash drop без разрешения конфликта = потерянная работа

**Контекст:** при попытке временно отложить правки через `git stash` для baseline-сравнения, последующий `git stash pop` дал warning о LF/CRLF и stash остался в очереди (а не удалился). Я сделал `git stash drop` — получил «Already up to date» по part of the changes; на самом деле сложился частичный мёрж и часть правок ушла в потерянный объект.

**Суть:** `git stash drop` после неуспешного `git stash pop` уничтожает блок в reflog. Восстанавливать через `git fsck --lost-found` → `dangling commit` → `git stash apply <hash>`. Но если на этот момент в working dir уже есть конфликтующие изменения — нужно сначала их сохранить отдельным stash.

**Применение:** перед `git stash drop` ВСЕГДА проверять `git status` и фактически файлы (не только git status, который может показывать лишь часть). Лучше использовать `git stash apply` (без drop) до явного подтверждения что всё на месте. Альтернатива — коммит локально в throwaway-branch, потом `git checkout main` и работа.

## [баг] Edit обрезает большие файлы если не прочитан через Read

**Контекст:** при правке extension.ts (4400+ строк) и других крупных файлов файлы обрезались до частично прочитанного фрагмента.

**Суть:** инструмент `Edit` требует предварительного `Read` именно через инструмент `Read` — `bash cat` не засчитывается. `Read` без параметров читает максимум 2000 строк. Если после этого вызвать `Edit` — инструмент знает только прочитанный фрагмент и пишет усечённый файл. Итог: всё что было ниже окна чтения — уничтожается.

**Применение:** для файлов >1000 строк — не использовать `Edit` напрямую. Вместо этого: читать оригинал из git (`git show HEAD:path > /tmp/orig`), делать точечные `str.replace()` в Python-скрипте, писать результат целиком. Это атомарно и не зависит от размера файла.

## «Верхний ползунок» / «ползунок бегает» — май 2026

**Контекст:** пользователь жаловался что «верхний ползунок бегает» пока «нижний спинер остановился». Потребовалось несколько попыток чтобы понять о чём речь.

**Суть:** «верхний ползунок» = тонкая полоска прогресса в заголовке панели WORKSPACES (встроенный индикатор загрузки VSCode). Появляется автоматически когда `getChildren()` TreeDataProvider выполняет `await` на асинхронный вызов. «Нижний спинер» = иконка синхронизации в статус-баре (`statusBar.setSyncing(true/false)`). Это два разных индикатора с независимым жизненным циклом.

**Применение:** когда пользователь говорит про «ползунок» в контексте панели воркспейсов — это панельный индикатор загрузки, не статус-бар и не окно VS Code целиком.

## Inline-кнопки дерева недоступны во время загрузки — май 2026

**Контекст:** пользователь сообщил что «триточки на воркспейсе не работают» пока «ползунок бегает».

**Суть:** VSCode блокирует ВСЕ inline-кнопки во всей панели пока `getChildren()` ожидает async-результат. Один медленный сетевой вызов (например `listRemoteWorkspaceSummaries`) в `buildCloudSectionElements` замораживает кнопки на всех элементах — включая локальные воркспейсы у которых нет сетевых зависимостей.

**Применение:** любой `await` внутри `getChildren` → панель тормозит. Решение: stale-while-revalidate (возвращать кеш мгновенно, обновлять в фоне).

## rebuildManifestFromLocalState воссоздаёт удалённый воркспейс — май 2026

**Контекст:** баг — воркспейс удалённый на одной машине появлялся снова на другой.

**Суть:** когда manifest NOT_FOUND в `syncWorkspace()`, код вызывал `rebuildManifestFromLocalState()` который **заново загружал манифест на облако**. Это правильно при случайной потере манифеста, но неправильно при намеренном удалении другой машиной. Различие: если папка воркспейса на облаке пустая/отсутствует → намеренное удаление → авто-отвязка; если папка есть но манифест отсутствует → accidental loss → rebuild.

**Применение:** при любых изменениях в `syncWorkspace()` помнить об этом разграничении.

## $(sync~spin) в дереве НЕ блокирует кнопки — май 2026

**Контекст:** при добавлении loading-спиннера для remoteOffer элементов.

**Суть:** иконка `$(sync~spin)` на tree item — просто анимированная иконка, она НЕ вызывает панельный индикатор загрузки и НЕ блокирует кнопки. Блокировку вызывает только `await` в `getChildren`. Для блокировки кнопок на конкретном элементе нужно менять `contextValue` так, чтобы `when`-условия в package.json не срабатывали.

**Применение:** для loading-состояния элемента использовать отдельный contextValue (например `vscodeSync.remoteOfferLoading`), а не полагаться на иконку.

## TTL-кеш remote summaries: invalidate нужен явно — май 2026

**Контекст:** добавление кеша для `_fetchRemoteSummaries` в `WorkspacesTreeProvider`.

**Суть:** после операций attach/delete воркспейса кеш нужно сбрасывать явно через `invalidateRemoteCache()`, иначе секция «Доступные на облаке» покажет устаревший список до истечения TTL (8 сек). Обычный `refresh()` кеш НЕ сбрасывает — только обновляет UI из кеша.

**Применение:** везде где меняется состав воркспейсов на облаке — вызывать `workspacesTree.invalidateRemoteCache()` перед `refresh()`.

## [договорённость] Убрать «Co-authored-by: Cursor» из коммитов

**Контекст:** Cursor автоматически добавляет строку `Co-authored-by: Cursor <noreply@cursor.com>` в сообщения коммитов.

**Суть:** создать git hook `.git/hooks/commit-msg` с содержимым:

```bash
#!/bin/sh
sed -i '/Co-authored-by: Cursor/d' "$1"
```

Затем сделать исполняемым: `chmod +x .git/hooks/commit-msg`. Hook работает в Git Bash / MINGW на Windows. Файл находится в `.git/hooks/` (не коммитится), поэтому нужно создавать заново при клонировании репо.

**Применение:** при настройке нового клона репозитория или если строка снова появляется в коммитах.

## [архитектура] Паттерн `dir/` в `ignoreMatch` не исключает файлы внутри каталога

**Контекст:** рекурсивное добавление папки в sync фильтруется через те же правила, что и одиночный файл; проверяли ожидание «`foo/` = весь подкаталог».

**Суть:** флаг `directoryOnly` в парсере лишь отрезает суффикс `/` у шаблона; сопоставление идёт как с полным `posixRel` файла. Шаблон вроде `a/b/` становится `a/b` и матчит только путь ровно `a/b`, не `a/b/file.ts`. Чтобы исключить дерево, нужны шаблоны уровня `a/b/**` или маски по имени файла.

**Применение:** документация для пользователей и тесты на ignore при bulk-add; при доработке матчера — не смешивать с семантикой git без явного решения.

**Контекст:** подменю с `resourceScheme == file && explorerResourceIsFolder` не показывалось при ПКМ по папке.

**Применение:** новые вклады в `explorer/context` для каталогов; отладка — Developer: Inspect Context Keys на ПКМ по папке.

## [баг] EPERM при атомарной записи JSON на Windows

**Контекст:** ошибка `EPERM: operation not permitted, rename '…vscodesync.json.*.tmp' -> '…vscodesync.json'` при сохранении конфига воркспейса.

**Суть:** на Windows `rename` поверх **уже существующего** файла часто возвращает EPERM/EACCES/EBUSY, пока у файла есть открытый handle (редактор, file watcher, индексатор, антивирус).

**Применение:** несколько попыток `rename` с backoff; если после этого всё ещё блокировка — для обычных JSON-конфигов допустим fallback на прямой `writeFile` тем же содержимым. Для lock-файлов без fallback — только retries.

## [архитектура] If-Match на blob не заменяет 3-way перед push

**Контекст:** после правок на одной машине «домашняя» копия успела залить старое содержимое в облако.

**Суть:** успешный PUT с `If-Match: текущий etag` лишь означает «замени эту ревизию blob»; если в `_meta` уже зафиксирован **новый** канонический хэш (другая машина успела), а локально на диске **старая** версия, etag всё равно совпадает с текущим blob — сервер примет перезапись. До upload нужна та же **трёхсторонняя проверка**, что в `syncOneFile` (`detectChange` + опциональный pull); явные keep-mine / auto-resolve передают признак и обходят проверку.

**Применение:** любые точки входа в `pushFile` (save, commit, offline queue); при доработке блокировок файла — reconcile вызывать **вне** `runWithSyncFileLock(..., "push")`, иначе `pullFile` в том же pipeline приведёт к deadlock.

## [баг] Сырой байт NUL в исходнике делает файл «бинарным» для git и grep

**Контекст:** аудит выдавал «этого нигде нет» по `syncEngine.ts`; при проверке оказалось, что поиск по файлу не возвращал вообще ничего.

**Суть:** в четырёх файлах разделитель ключа был записан **сырым байтом** NUL, а не escape-последовательностью. Любой файл, содержащий NUL, git классифицирует как binary: `grep`/`rg` без `-a` молча пропускают его, `git diff` показывает «Binary files differ» вместо содержимого, а правило `text=auto` **отказывается нормализовать** ему переводы строк. Файл при этом нормально компилируется и работает — дефект видим только инструментам.

**Применение:** невидимые символы в коде писать только escape-записью (`\u0000`, `\u0001`, `\uE000`), никогда самим байтом. Класс закрыт тестом `tests/unit/sourceHygiene.test.ts`; предикаты в нём написаны через коды символов, а не литералами в регулярке — литерал внёс бы в файл ровно те байты, которые файл запрещает, и тест падал бы на самом себе. Если поиск по большому файлу подозрительно ничего не находит — сначала `file <path>`: ответ `data` вместо `text` означает ровно это.

## [vscode] `OutputChannel` — write-only, прочитать журнал нечем

**Контекст:** support bundle обещал «последние 5000 строк OutputChannel» и не содержал их.

**Суть:** у `vscode.OutputChannel` нет ни одного API чтения — только `append`/`appendLine`/`clear`. Всё, что ушло в канал, для расширения потеряно. Единственный способ положить журнал в диагностический архив — вести параллельный кольцевой буфер в памяти рядом с записью в канал.

**Применение:** любой артефакт «приложите логи» проектировать сразу с буфером (`src/utils/logVscode.ts`, `readRecentLogLines`). То же касается health-check и подобных отчётов: печатать в канал недостаточно, нужен in-memory снимок (`src/core/lastHealthReportStore.ts`), причём заполнять его **внутри** генератора отчёта, а не на стороне вызывающих — иначе один из вызовов рано или поздно забудут.

## [баг] `@vscode/test-electron` 2.x не запускает VS Code 1.110+ на macOS

**Контекст:** интеграционный тест падал с `spawn .../Contents/MacOS/Electron ENOENT` сразу после скачивания VS Code.

**Суть:** версии 2.x ищут исполняемый файл по жёсткому пути `Visual Studio Code.app/Contents/MacOS/Electron`. Сборки VS Code 1.110 и новее кладут его под именем продукта — `Contents/MacOS/Code`. Скачивание при этом проходит успешно, поэтому ошибка выглядит как проблема окружения, а не как несовместимость версий.

**Применение:** `@vscode/test-electron` от 3.1.0 — он резолвит бинарь по содержимому `Contents/MacOS/`. Симптом «ENOENT на Electron сразу после Downloaded VS Code» = устаревший раннер, а не сломанный Xcode или права доступа.

## [договорённость] Мёртвые настройки перечисляются поимённо, а не замалчиваются

**Контекст:** 16 из 98 объявленных настроек не читаются кодом ни разу — пользователь их меняет, и не происходит ничего.

**Применение:** при добавлении настройки — сразу подключать; при удалении фичи — вычищать ключ из схемы и из `UNWIRED`. Долг остаётся видимым, а не растворяется.

## [архитектура] Необязательный параметр — это не «гибкость», а гарантированный забытый вызов

**Контекст:** ключ шифрования был необязательным пятым аргументом `makeEngine`. До движка он доезжал в 7 местах создания из 24; в шести местах его нельзя было передать физически — параметра не было в типе зависимостей.

**Суть:** поля `encrypt`/`decrypt` в `SyncEngineDeps` были опциональными, поэтому движок, собранный без них, спокойно работал открытым текстом. Никакой ошибки, никакого предупреждения. При включённом шифровании автотриггеры (push после сохранения, pull при открытии, focus-синхронизация, push коммита, флаш очередей, миграция между облаками, рендер дерева) заливали **открытый текст поверх зашифрованных блобов** — с корректным `_meta.hash`, поэтому ничего никогда не исправляло, — и писали **шифротекст поверх файла пользователя** при pull. Это же объясняло «то могу отправить, то нет»: ручные команды шли через путь с ключом и работали.

**Применение:** секрет или обязательный ресурс не передавать параметром, который можно опустить. Владельцем должен быть тот, кто умеет его получить (здесь — фабрика движка, `registerEncryptionKeyRefresh`), а потребитель должен уметь отличить «выключено» от «включено, но недоступно» и отказать во втором случае (`encryptionRequired` + `assertEncryptionReady`). Проводку чинить недостаточно: нужен барьер, который переживёт следующую поломку проводки.

## [баг] Тост с кнопкой не закрывается сам и держит `finally`

**Контекст:** статус-бар залипал в «Синхронизация…» после ошибки любой команды.

**Суть:** в `_runWithEngine` ветка ошибки делала `await vscode.window.showErrorMessage(..., "Войти снова")`, и только потом шёл `finally` со сбросом спиннера и обновлением дерева. Промис нотификации с кнопкой резолвится **лишь когда пользователь её закроет**; сам тост уходит в центр уведомлений и висит там сколько угодно. Это обёртка всех 167 команд.

**Применение:** обновление UI никогда не ставить за `await` нотификации. Показ диалога — после восстановления состояния и, если диалог лишь предлагает действие, без `await` вообще. Симметрично: `setSyncing`-подобные флаги, которые дёргают несколько независимых источников, должны быть счётчиками вложенности с watchdog'ом, иначе кто завершился первым — погасил индикатор всем.

## [баг] `@vscode/test-electron` 2.x и потолки, которых не было

**Контекст:** три источника «бесконечного» ожидания, найденные в одном проходе.

**Суть:** (1) `fetchWithTimeout` снимал таймер в `.finally()` промиса `fetch`, который резолвится на **заголовках**, — всё чтение тела шло с разоружённым `AbortController`; в desktop-хосте undici перезапускает `bodyTimeout` на каждом чанке, поэтому у «струйки» байтов потолка нет вовсе. (2) `RequestQueue` по умолчанию имел `timeoutMs = 0`, то есть сторож не создавался, а слот освобождался только по завершении операции — один незавершившийся запрос вешал очередь навсегда. (3) `runWithSyncFileLock` не имел ни дедлайна ожидания, ни дедлайна выполнения, а карта FIFO-хвостов не чистилась никогда.

**Применение:** при дедлайне выполнения файлового лока вызывающему возвращается ошибка, но **ключ остаётся занятым** до фактического завершения зависшего тела: освободить раньше — значит разрешить второй push поверх файла, который первый ещё пишет. Зависшая операция дешевле битого файла. Тот же принцип применим везде, где «отпустить блокировку по таймауту» выглядит очевидным решением.

## [архитектура] Политику мутаций нельзя инжектировать — иначе она станет следующим bypass-параметром

**Контекст:** этап 3.1, находка F2. До неё инвариант «расширение не двигает файлы само» не был закреплён нигде, а обходился в нескольких местах сразу: смена git-ветки пушила и пуллила мимо `autoSyncMode`, флаши очередей передавали `bypassSchedule` / `bypassAutoPause` / `bypassRateLimit`, задача `vscodesync` с `runOn: folderOpen` доходила до `pushAll` вообще без гейта.

**Суть:** план аудита предлагал поле `SyncEngineDeps.mutationPolicy: (op, trigger) => "allow" | "deny"`. Это повторило бы ту же ошибку на уровень выше: политика, которую вызывающий подставляет сам, — не политика, а ещё один параметр обхода. Решение принимает чистая функция в `src/core/syncPolicy.ts`, движок импортирует её напрямую, подменить нечем. Через зависимости приходит только **факт** — `trigger: "user" | "auto"`, и он **обязателен** (см. [архитектура] про необязательный параметр: `encKey` был опциональным и его забыли в 17 местах из 24). Обязательность заставила компилятор задать вопрос всем 23 местам сборки движка. Второе следствие того же принципа: прямых сравнений `trigger === "user"` внутри `src/core/` быть не должно — это второй центр решения; для «пропустить, а не упасть» есть непубличная `mayMutate(op)`, которая всё равно спрашивает `mutationPolicy`.

**Применение:** гейт `tests/unit/mutationPolicyGate.test.ts` сверяет рантайм-список `MUTATION_OPS` с фактическими вызовами `assertMayMutate` в движке, ловит возврат `bypass*`, требует явный литерал триггера на каждом вызове `makeEngine` и держит список модулей, которым позволено умолчание `"user"` в `runWithEngine`. Союз объявлен рантайм-массивом (`as const`), а не типом: тип пришлось бы восстанавливать разбором текста файла, а текстовый парсер тихо перестаёт совпадать после первого же переформатирования.

## [архитектура] «Только проверка» не значит «ничего не пишет»

**Контекст:** при вводе чекпоинта нужно было решить, гейтить ли `syncWorkspace` целиком. Оказалось, что `checkWorkspaceStatus` — это одна строка `return this.syncWorkspace(id, { checkOnly: true })`, то есть запрет на метод убивает фоновый детектор расхождений вместе с ним.

**Суть:** ветка `checkOnly: true` вопреки названию писала три разные вещи. (1) **В облако** — пролог метода безусловно сливал очередь отложенных снимков истории (`runDeferredHistorySnapshots` → `uploadFile` + `deleteFile` в `pruneHistory`), причём до всякой проверки `options`. (2) **Состав трекинга** — `adoptManifestFilesFromCloud` добавляет записи по чужому манифесту, `pruneTrackingFromManifest` удаляет, а при NOT_FOUND манифеста ветка сносила воркспейс целиком через `detachWorkspaceLocal`. (3) Собственно статусы, ради которых всё и затевалось. Первое и третье исправлены (слив истории ждёт пользовательского прохода; отвязка при NOT_FOUND сообщается, но не выполняется фоном). Второе осталось названной дырой: гейт на нём валит детектор, правильное решение — расцепление, а не запрет.

**Применение:** прежде чем объявлять путь «read-only», проследить его до провайдера и до `saveCfg`, а не полагаться на имя метода и на флаг в параметрах. Формулировка «check-only только считает расхождения» в пользовательской документации до расцепления некорректна. Условный гейт (`if (options?.checkOnly !== true)`) — единственное исключение и объявлен в `CONDITIONAL_GATES` гейт-теста поимённо, чтобы не стал образцом для подражания.

## [договорённость] Задачи `vscodesync` мутируют только по отдельному разрешению

**Контекст:** `tasks.json` с `"runOptions": {"runOn": "folderOpen"}` — штатная возможность VS Code. Задача типа `vscodesync` при этом доходила до `pushAll` / `pullAll` при открытии окна, проходя через ту же обёртку `runWithEngine`, что и 167 команд палитры, то есть выглядела для движка человеком.

## [баг] Кэш тела и кэш etag с разными владельцами — устаревшее тело на 304

**Контекст:** «Применить» после отчёта детектора о дрейфе трекинга ничего не делал. Etag манифеста хранится в общем на корень конфиг-сторе (его продвигает любой инстанс движка через `patchEntry`), а тело манифеста — в per-instance `manifestByWs`.

**Суть:** инстанс A скачал манифест и продвинул etag в общем сторе. Инстанс B, у которого в кэше лежит более старое тело, шлёт условный GET с чужим свежим etag, получает 304 и «удовлетворяет» его из своего кэша — телом, которому этот etag никогда не соответствовал. 304 доказывает только «облако совпадает с присланным etag», а не «облако совпадает с твоим кэшем». Исправление: тело в кэше привязано к своему etag (`manifestEtagByWs`), кэш отвечает на 304 только при совпадении, иначе полная перезагрузка. Тот же класс бага в `setSoftLock`/`clearSoftLock`: между `downloadManifest` (который уже обновил etag в сторе) и `putManifest` использовался etag, считанный до скачивания, — каждая запись лока шла через 412-merge.

**Применение:** если разные уровни кэша (общий стор + память инстанса) хранят части одного факта (etag + тело), каждая запись обязана обновлять их атомарно, а чтение — проверять согласованность. Хелперы `cacheManifest`/`evictManifestCache`/`currentManifestEtag` — единственные точки касания.

## [архитектура] Merge манифеста при равных версиях отдаёт победу удалённой строке — presence в manifest это ловушка

**Контекст:** после отказа от инкремента `version` в `setSoftLock` лок перестал доезжать до облака: запись шла через 412-merge, а `mergeManifestFiles` при равных `version` и `addedAt` выбирает удалённую строку — без editingBy.

**Суть:** merge разрешает конфликт по `version`, задуманному для контента. Метаданные присутствия (editingBy/editingSince) не повышают версию (иначе каждое переключение вкладки инфлирует «у кого новее» — исходный дефект B4), значит на любом merge они проигрывают. Ночное решение: не доводить запись лока до merge (свежий etag → putManifest без 412). Фундаментально presence в манифесте — жилец не по адресу; при рефакторинге этапа 5 просится в `_machines.json`/отдельный объект.

**Применение:** прежде чем класть новое поле в манифест, проверить: повышает ли его изменение `version`? Если нет — поле молча теряется на каждом 412-merge.

## [архитектура] Детекторный путь не имеет права ставить что-либо в очередь

**Контекст:** после 3.4 триггеры save/open/commit стали детекторами (`checkWorkspaceStatus`), но обёртка `withEngine` сохранила старую обработку ошибок от времён, когда те же триггеры пушили файлы.

**Суть:** в catch остались две ветки: сетевая ошибка → `enqueuePush/enqueuePull`, а `UNAUTHORIZED` → `enqueueFullSync()`. Вторая срабатывала на *детекторном* проходе: пользователь с протухшим токеном сохранял файл — и в оффлайн-очереди появлялся «полный sync», которого он не заказывал. Поскольку очередь после B2 — это список отложенных **намерений пользователя**, чужой `fullSync` хоронил под собой его настоящие push/pull. Правильное поведение: пересчёт, который не смог выполниться, повторять нечего — следующий триггер пересчитает сам.

**Применение:** при переводе действия в детектор проверять не только тело операции, но и её обработку ошибок: retry-логика, очереди, backoff — всё это осмысленно только для действий. Общий признак ошибки — фон создаёт запись, которую пользователь потом увидит как «своё намерение».

## [договорённость] Решающая часть одноразовой миграции живёт отдельно и тестируется

**Контекст:** `migrateSettingsTo100` выполняется ровно один раз на машину и пишет маркер в `globalState` даже при частичных сбоях. Разработчик, получивший баг-репорт, воспроизвести её у себя не может.

**Суть:** решение («что переписать, что вычистить, в каких scope») вынесено в чистый `src/core/settingsMigrationPlan.ts` — функция от снапшота `inspect`-значений к списку действий. Стартовый модуль только исполняет план и показывает тосты. Побочный эффект нужного свойства: план строится только для реально существующих значений, поэтому повторный прогон даёт пустой план — идемпотентность по построению, а не по флагу. Тесты закрывают folder-scope (multi-root), falsy-значения (`false`/`""`/`0` — установлены, а не отсутствуют) и сверку списка удаляемых ключей со схемой.

**Применение:** любая одноразовая миграция должна разделяться на «решить» и «исполнить». Проверка «сколько раз можно безопасно прогнать» решается формой плана, а не маркером: маркер защищает от повторных тостов, идемпотентность — от порчи данных.

## [архитектура] «Keep Mine» нельзя починить, просто убрав обход 3-way сверки

**Контекст:** этап 3.6, дефект D5. `reconcileBeforePushUpload` начинается с `if (activityHint?.asAutoResolvedKeepMine) return true;` — то есть разрешение конфликта «оставить моё» заливает файл без сверки и затирает то, что вторая машина запушила после отметки конфликта.

**Суть:** очевидная правка (снять обход) ломает фичу целиком. Конфликт по определению означает `base ≠ local` и `base ≠ cloud`, поэтому `detectChange` на том же входе снова вернёт `"conflict"` — Keep Mine перестанет работать вообще, а не станет аккуратнее. Обход не баг, а следствие того, что у команды нет точки отсчёта: «облачная версия, которую пользователь решил отбросить» и «версия, появившаяся уже после его решения» неразличимы. Решение — запомнить облачный хэш в момент отметки конфликта (`TrackedFile.conflictCloudHash`, ставится в трёх местах; на 412-пути он `undefined`, потому что облако там не читалось) и сверять с ним перед заливкой. Отдельно: `resolveConflictKeepMine` рапортовал успех и тогда, когда `pushFile` внутри ловил 412 и возвращал файл в конфликт — метод теперь читает статус после пуша и отдаёт `cloud_moved`.

**Применение:** прежде чем снимать «странный» обход проверки, проверить, не является ли проверка логически несовместимой с намерением команды. Если да — недостающее звено обычно не в проверке, а в отсутствии сохранённого состояния, на которое можно опереться.

## [архитектура] Принимающая сторона не имеет права писать в рабочее дерево

**Контекст:** этап 3.6, остаток B15 и дефект D7. P2P-приёмник писал файл пира прямо в воркспейс; Quick Transfer «Получить» молча перезаписывал существующий локальный файл и удалял облачный пакет до записи.

**Суть:** у обоих путей момент записи выбирает не пользователь, а отправитель. Одинаковая форма лечения: (1) разделить «получить байты» и «применить» — в P2P это staging-папка `.vscode/vscodesync-incoming/<transferId>/`, в Quick Transfer — `prepareQuickTransferReceive`, который ничего не пишет и сообщает `destExists`; (2) удаление источника — только после успешной локальной записи; (3) приём чужих файлов — за настройкой с дефолтом `off` (`vscodesync.p2p.acceptIncomingFiles`), причём выключенная настройка означает «приёмник не подключён», а не «подключён и молчит». **Применение:** любой входящий канал (P2P, Quick Transfer, вебхук, импорт) описывать тройкой «стейджинг → решение пользователя → применение с бэкапом». Если код умеет писать в рабочее дерево по сетевому событию — вопрос не «безопасен ли путь», а «кто выбрал момент».

## [провайдер] Implicit flow не чинится настройкой — он не выдаёт refresh-токен вовсе

**Контекст:** этап 4.2, дефекты E2 и E3. Вход в Яндекс.Диск шёл через `response_type=token`, и в бандл писался только `accessToken`.

**Суть:** это не «недонастроенный OAuth», а другой протокол. Условие `bundle.expiresAtMs - Date.now() < skew && bundle.refreshToken` было вечно ложным, поэтому `accessToken()` спокойно отдавал заведомо протухший токен, `refreshAccessToken` оставался недостижимым кодом, а реактивный refresh по 401 не мог сработать в принципе. Второй дефект был следствием первого: implicit отдаёт токен во фрагменте URL, который видит только браузер, поэтому потребовался HTML-шим, POST-ящий токен на локальный сервер, — а тот принимал что угодно (ни `state`, ни `Origin`, ни `Content-Type`) на фиксированном порту 8735. Cross-origin form-POST с `enctype=text/plain` — простой запрос без preflight — позволял подсунуть чужой токен, и файлы поехали бы в чужой Диск. Перевод на authorization code + PKCE убрал и мёртвый refresh, и шим целиком: код приходит query-параметром, `state` проверяет общий `runPkceLoopbackOAuth`, обмен идёт из extension host.

**Применение:** увидев «refresh не работает» — сперва проверить `response_type` в authorize-URL, а не логику refresh. И: HTML-шим на loopback — почти всегда признак implicit-потока и всегда требует проверки происхождения.

## [архитектура] Один инстанс провайдера на всех + пять фоновых задач = гонка за SecretStorage

**Контекст:** этап 4.2, дефект E4. `grep 'refreshPromise|pendingRefresh|Mutex'` по `src` давал ноль, при этом `registry.ts` мемоизирует один инстанс провайдера для всех потребителей.

**Суть:** на старте почти одновременно просыпаются 5+ фоновых задач; каждая зовёт `accessToken()`, каждая видит «токен скоро истечёт» и запускает свой refresh. Побеждает последняя запись в SecretStorage — а у провайдеров, ротирующих refresh-токен (Dropbox, Google), бандл проигравшего уже отозван. Лечится мьютексом в `providers/_shared/tokenStore.ts`: `refreshOnce` делит один in-flight запрос, слот освобождается и при успехе, и при ошибке. Важная деталь: входить в мьютекс нужно **только когда refresh действительно нужен** — иначе принудительный refresh по 401 присоединится к уже летящему no-op вызову и получит тот же мёртвый токен (для OneDrive это отдельный предикат `needsOneDriveRefresh`).

**Применение:** любой мемоизированный синглтон, который пишет в общее хранилище, нуждается в сериализации записи. Проверка «есть ли гонка» — не «зовут ли метод параллельно», а «сколько независимых потребителей держат один инстанс».

## [провайдер] Ретрай-политика видит только то, что ей бросили

**Контекст:** этап 4.3, дефекты E8 и E5. У Google Drive `driveFetch` уже был обёрнут в `withRetry`, и всё равно троттлинг не ретраился.

**Суть:** обёртка `withRetry` реагирует на исключения. Google сообщает о троттлинге как о **403 с причиной в теле** (`rateLimitExceeded`, `userRateLimitExceeded`, `sharingRateLimitExceeded`), а проверка внутри обёртки смотрела только на 429/503 — поэтому 403 не бросался, возвращался вызывающему как обычный ответ, и тот превращал его в NETWORK_ERROR уже **снаружи** конверта. Ни ретрая, ни взведённого rate-limit-гейта. Симметричный случай: переполнение (403 `storageQuotaExceeded`, 507) попадало под общий 5xx-фильтр и ретраилось, хотя повторять его бессмысленно. Лечение — общий `inspectProviderResponse`, который классифицирует ответ **до** возврата и бросает то, на что политика обязана отреагировать, а 404/412/423 отдаёт вызывающему как осмысленные для него состояния.

**Применение:** проверяя «почему не ретраится», сначала выяснить, доходит ли ошибка до конверта в виде исключения. И: список статусов, которые обёртка распознаёт, должен собираться из документации конкретного API, а не из общего представления об HTTP.

## [провайдер] Чтение, которое создаёт папки, — не чтение

**Контекст:** этап 4.4, дефект B16. У Google Drive `listFolder → ensureFolderPath → ensureChildFolder` при промахе делал `POST /files`.

**Суть:** двенадцать читающих вызывающих (среди них `connectivityProbeWidget` — **каждые 30 секунд**) через якобы безопасный `listFolder` создавали в чужом Google Drive структуру папок, включая корневой `VSCodeSyncFiles`. У трёх других провайдеров `listFolder` — чистое чтение, поэтому расхождение не замечали. Разделение на `resolveFolderPath()` (поиск, `null` при отсутствии) и `ensureFolderPath()` (создание) — не рефакторинг ради красоты: «папки нет» и «папку надо создать» это разные ответы, и выбирать между ними должен вызывающий. ## [архитектура] Необязательный параметр — это разрешение его забыть

**Контекст:** этап 5.0. `createWorkspaceSnapshot` заливал файлы в облако открытым текстом при включённом `vscodesync.encryption`: движок шифровал блобы, снапшоты — нет.

**Суть:** дело не в том, что кто-то «забыл вызвать encrypt» в одном месте — функция вообще не принимала контекст шифрования, и все восемь точек вызова были одинаково беззащитны, включая три автоматические (перед merge, перед ротацией ключа, по расписанию). Лечение — сделать `SnapshotCrypto` **обязательным** параметром: компилятор сам перечислил все восемь мест, и каждое пришлось осознанно закрыть. Соблазнительная альтернатива — модульный провайдер, устанавливаемый при активации (как `setTrackedPathMachineNameProvider`) — здесь была бы хуже: она снова прячет решение и не даёт гарантии на новых вызовах. Второй урок: формат должен помнить, как он записан. Поле `encryption` в мете снапшота позволяет старым (незашифрованным) снапшотам восстанавливаться, а новым — не восстанавливаться без ключа; догадываться по «получилось ли расшифровать» нельзя, потому что «не получилось» неотличимо от «это был plaintext».

**Применение:** когда правишь пропущенную обязанность (шифрование, санитизация, проверка прав) — сначала посмотреть, была ли она вообще выразима в сигнатуре. Если нет, чинить надо сигнатуру, а не вызов. И: любая смена формата на диске/в облаке требует поля-маркера, иначе обратная совместимость держится на угадывании.

## [баг] Продублированное решение расходится в термине, который выглядит избыточным

**Контекст:** этап 5.1, дефект C17. Решение «push / pull / conflict» принималось в четырёх местах движка, и три из них были почти копией четвёртого.

**Суть:** расхождение свелось к одному конъюнкту. Страховка «консенсус ушёл вперёд, наш кэш отстал» в строгом варианте звучит так: `base есть && cachedLocalHash !== base && cloudHash === base && localHash !== cloudHash`. Последний терм в трёх копиях отсутствовал — и выглядит он избыточным ровно до сценария «файл правили и вернули к исходному»: тогда `cachedLocalHash` устарел навсегда, а содержимое уже совпадает с облачным. Без терма ответ «pull» повторяется вечно: панель показывает «↓1», Pull ничего не меняет, следующий тик снова рисует «↓1». Код сам признавал дубль комментарием со ссылкой на номера строк соседней копии — и эти номера к моменту разбора давно протухли.

**Применение:** комментарий «такая же проверка есть в X:1234» — это заявка на дефект, а не документация. Если проверку нельзя вызвать из одного места, значит, её надо вынести. И при сверке копий сравнивать не «смысл», а конъюнкты по одному: расхождение обычно в термине, который в двух из трёх сценариев ничего не меняет.

## [провайдер] ETag — это не хэш, и проверка целостности по нему всегда ложная

**Контекст:** этап 4.6, дефект E10. При включённом `vscodesync.providerHashVerify` каждый push на OneDrive падал с `INTEGRITY_FAILED` — после **успешной** заливки.

**Суть:** проверка сравнивала `meta.etag` с локально посчитанным хэшем содержимого. Но `etag` — непрозрачный токен версии, а не дайджест: у Graph это `{GUID},N`, у Dropbox — `rev`. Совпасть с md5/sha они не могут в принципе. Код это чувствовал и защищался эвристиками — «сравним со всеми алгоритмами сразу» и «ругаемся только если строка длиннее 32 символов», — которые маскировали проблему ровно до провайдера, у которого etag случайно и есть md5 (Drive, Яндекс). Правильное решение — отдельное поле `contentDigest: { kind, value }`, заполняемое из того, что API **определяет** как хэш: Graph `file.hashes`, Dropbox `content_hash`, Drive `md5Checksum`, Яндекс `md5`. Провайдер без дайджеста поле не заполняет, и проверка честно пропускается вместо угадывания.

**Применение:** сверяя целостность, брать поле, у которого в документации API написано «хэш содержимого». Если приходится определять вид значения по длине или по регулярке — используется не то поле. Тот же признак работает и в обратную сторону: эвристика «похоже на md5» в коде почти всегда означает, что рядом лежит правильное поле, которое никто не прочитал.

## [архитектура] Отмена — это не флаг в UI, а параметр, доходящий до сокета

**Контекст:** этап 1, дефект A5. Кнопка «Отмена» была у трёх команд из 167 и ни одну операцию физически не останавливала.

**Суть:** `fetchWithTimeout` умел принимать `AbortSignal` с самого начала — просто никто его не передавал, и на всём пути от команды до сокета не было ни одного места, где сигнал мог бы появиться. Арифметика без отмены: 3 попытки × 120 с таймаута + `Retry-After` до 300 с между ними ≈ 16 минут на **один** запрос, и `listFolder` повторял это на каждой странице. Работающая отмена собирается из четырёх частей, и без любой из них она декоративна: (1) сигнал доходит до транспорта — тогда прерывается запрос в полёте; (2) циклы проверяют отмену **между** единицами работы — иначе после отмены стартует ещё сотня файлов; (3) сон между ретраями прерываем — иначе отменённая операция досыпает пять минут молча; (4) отмена отличается от ошибки в отчёте пользователю — иначе он получает диалог сбоя за собственное нажатие. Отдельная деталь: `Retry-After` нужно ограничивать сверху, иначе вежливость к провайдеру оплачивается заморозкой команды на минуты.

**Применение:** проверяя «есть ли у нас отмена», идти не от кнопки, а от сокета вверх: где сигнал рождается, кто его принимает, что делает цикл. И: `signal?.aborted` внутри цикла надо читать через функцию — TypeScript сузит флаг до `false` после первой проверки и объявит вторую мёртвым кодом, хотя меняется он асинхронно.

## [провайдер] Неизвестное поведение API лечится не прогоном, а снятием зависимости

**Контекст:** этап 4.6, дефект E11. План требовал прогона против живого Google Drive: отдаёт ли Drive v3 заголовок `ETag` на PATCH и multipart-POST. Доступа к живому аккаунту нет.

**Суть:** вопрос был поставлен неправильно. Опасность состояла не в самом заголовке, а в том, что `syncEngine` делает `etag = res.etag ?? etag` — отсутствующее значение молча сохраняет **прежний** etag, и следующий условный запрос сравнивается с версией, которой уже нет. Пока ответ зависит от недокументированного поведения чужого сервиса, код остаётся хрупким независимо от того, какой ответ получен сегодня: завтра Drive может перестать слать заголовок. Правильный ход — попросить у API то, что он обязан вернуть по документации (`fields=id,md5Checksum`), и брать версию оттуда; заголовок принимается, если есть, но ничто на нём не держится. Заодно выяснилось, что фолбэки на `DriveFileSummary.etag` были мёртвым кодом: ни один `fields=` в провайдере это поле никогда не запрашивал.

**Применение:** пункт вида «нужно проверить на живом API, делает ли он X» — сигнал, что код зависит от X. Прежде чем добывать доступ, спросить: можно ли переписать так, чтобы X перестал влиять? Если да — это дешевле, надёжнее и не устареет вместе с чужим сервисом.

## [архитектура] Идентичность файла и его размещение — разные факты с разными механизмами сходимости

**Контекст:** 2026-08-11, Link Bindings (этап 1). Файл в синке был ключован относительным путём во всех четырёх пространствах сразу: манифест, `_meta`, blob, локальный диск.

**Суть:** развязка потребовала три РАЗНЫХ механизма сходимости, и выбор каждого неочевиден. (1) `linkId` легаси-строк бэкфиллится **детерминированно** (`sha256(path+"\0"+addedAt)`) и **без bump version**: сходимость даёт сам детерминизм — две машины запишут одно и то же, а bump заставил бы каждый бэкфилл драться с реальными правками в 412-merge. (2) `bindings` мержатся **по-ключевым LWW на `boundAt`**, а не победой строки по Lamport: перепривязка, гонящаяся с несвязанной правкой той же строки (soft-lock, метка), при row-LWW молча терялась. (3) Отвязка — **запись** своего ключа с каноническим значением, никогда не удаление: удаление + union-merge воскрешает ключ из любой старой копии. Правки, которые пользовательские (bind, переименование метки), бампают version как обычно.

**Применение:** добавляя в мержимую структуру новое поле, выбирать механизм сходимости по природе поля: детерминированно вычислимое — без версий; пер-акторная карта — по-ключевой LWW; смысловая правка — Lamport. Один механизм «на всё» ломается на первом же поле другой природы.

## [архитектура] Хэш канонического содержимого зависит от ПУТИ — привязки обязаны хэшировать по каноническому ключу

**Контекст:** 2026-08-11, Link Bindings, свип точек ключевания (153 must-change сайта по результатам мультиагентной инвентаризации).

**Суть:** `canonicaliseToHashableBytes` решает «бинарный или текст» по расширению пути, и от этого зависит нормализация переводов строк — то есть сам хэш. Пока локальное имя всегда совпадало с облачным, `computeHash(absPath)` был безопасен. С привязками файл может называться локально иначе — и машина, хэширующая по локальному имени, разойдётся в хэшах с машиной, хэширующей по каноническому, на одном и том же содержимом. Лечение: единый `hashTrackedFile(abs, manifestKey)` — байты с диска, правила по каноническому ключу. Тот же класс ошибки — `planUploadEncoding` (решение о gzip по расширению) и presence/soft-lock (сравнение relPath между машинами — только в каноническом пространстве).

**Применение:** любая функция, принимающая «путь» файла, должна объявлять, ЧТО она из него читает: байты (локальное пространство) или правила/ключи (каноническое). Гейт `tests/unit/manifestKeyUsage.test.ts` держит регрессию по запрещённым паттернам ключевания.

## [договорённость] Чужое переименование в облаке никогда не двигает локальные байты

**Контекст:** 2026-08-11, Link Bindings этап 3, реплей canonical rename.

**Суть:** до фичи чужое переименование молча переезжало трекинг: файл числился по новому пути, на диске лежал по старому, «осиротев». Договорённость: если байты реально лежат на диске — при реплее переезжает только КЛЮЧ (через привязку), а физический перенос файла предлагается тостом «Переместить у меня / Оставить мою структуру» и выполняется `workspace.fs.rename` строго по клику. **Применение:** любой автоматический реплей чужого решения проверять вопросом «что здесь физически лежит у пользователя?» — метаданные можно пере-ассоциировать молча, байты двигаются только явно.

## [баг] Условная запись (`ifMatch`) на пути «перезаписать несмотря ни на что» даёт вечный круг

**Контекст:** 2026-08-11, жалоба владельца: окно «на облаке версия новее» всплывало по кругу, «Всё равно оставить моё» не срабатывало. Дефект жил с v0.4.0.

**Суть:** `pushFile` всегда слал `ifMatch` с etag из `_meta`. Для «оставить моё» это логическое противоречие: кнопка существует ровно для случая «облако ушло вперёд», а `ifMatch` в этом случае гарантированно даёт 412. Ветка обработки 412 заново поднимала конфликт и обнуляла `conflictCloudHash` — следующее нажатие проходило проверку «облако сдвинулось?» (baseline пуст → false), снова упиралось в 412, и цикл замыкался. Признак класса: **защита от перезаписи стоит на пути, чья единственная цель — перезаписать**. Лечение: `ifMatch` не ставится, когда пользователь уже подтвердил перезапись; сохранность закрывается тем, что прежняя облачная версия копируется в `.history` до заливки.

## [архитектура] Атомарность батча кодируется в форме данных: один Lamport-version на весь переезд

**Контекст:** 2026-08-12, правка канонических путей (docs/v3/canonicalPaths.md), выбор механизма сходимости для папочного rename.

**Суть:** папочный переезд — это N пар «tombstone + наследник». Если каждая пара получает свой `version`, конкурирующие переезды одной папки с двух машин сходятся *пофайлово* — часть файлов уезжает в `app/`, часть в `core/`, папка «рвётся». Лечение без нового кода на стороне читателя: ВСЕ строки батча (tombstone-ы и наследники) несут ОДИН version и один timestamp — тогда обычный row-LWW merge, включая merge старого клиента и третьей машины, решает судьбу всей папки одинаково. Альтернатива (журнал операций с rebase-композицией) была спроектирована и отклонена судьями: четвёртый механизм сходимости ради UX-точности, которую дают материализованные пары + linkId-спаривание.

**Применение:** когда группа записей должна выживать или проигрывать merge целиком — дать им одну версию, а не полагаться на транзакционность писателя: форма данных исполняется каждым читателем, транзакция — только автором. Проверка — property-тест на порядок merge (tests/unit/canonicalRenameConvergence.test.ts).

## [архитектура] Идемпотентный многошаговый облачный джоб: разрушающий шаг — строго последним

**Контекст:** 2026-08-12, порядок канонического переезда (io/canonicalRelocation.ts); старый renameTrackedFile удалял блоб ДО putManifest.

**Суть:** переезд ключа трогает четыре облачных объекта (блоб, история, манифест, `_meta`) и не может быть атомарным. Порядок выбирается так, чтобы обрыв на ЛЮБОМ шаге оставлял состояние, из которого повтор тех же входных данных доводит работу: сначала копии на новые места (повтор перезапишет), затем оба документа, и только последним — удаление старых блобов. Обрыв до удаления оставляет сироту-копию (безвредно, GC-able); обрыв старого порядка оставлял манифест, указывающий на удалённые байты — невосстановимо без ручного вмешательства. Плюс «missing source = уже сделано»: планировщик классифицирует отсутствующий источник как пропуск, а не ошибку, поэтому «Возобновить перенос» — это буквально повторный вызов с теми же аргументами.

**Применение:** любой многообъектный облачный джоб проектировать от вопроса «что увидит повтор после обрыва на шаге K?» — и никогда не удалять источник раньше, чем оба каталога (манифест и мета) укажут на копию.
