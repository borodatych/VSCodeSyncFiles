## [архитектура] Логгер decoupled от vscode

**Контекст:** при создании centralised logger через `OutputChannel` и импорте его из `src/utils/log.ts` сборка CLI падала с `Could not resolve "vscode"` — CLI бандл (`cli/src/main.ts`) транзитивно тянул `log.ts` через провайдеры (yandexDiskProvider).

**Суть:** `src/utils/log.ts` НЕ должен импортировать `vscode`. Базовый logger хранит абстрактный `LogSink` с no-op default; VS Code-обвязка живёт в отдельном `src/utils/logVscode.ts` и регистрируется при `activate(...)` через `setLogSink`. CLI и тесты получают тихий no-op без падения.

**Применение:** любой shared utility, который импортирует `vscode`, не должен использоваться из общего кода поверх провайдеров; либо decoupling через инъекцию, либо отдельный файл-обвязка.

## [баг] Lint flow-narrowing считает мутируемые-извне поля недостижимыми

**Контекст:** `webhookTunnel.ts:69` — поле `disposed: boolean` устанавливалось извне (`dispose()`), но проверка `if (state.disposed) return` внутри `connect()` после `if (state.disposed) return` в начале функции трактовалась eslint как «всегда falsy».

**Суть:** typescript-eslint flow-analyser не учитывает мутации через side-effect. Чтение `state.disposed` напрямую сужается до literal `false` после первой проверки. Решение — спрятать чтение за функцию-геттер: `function isDisposed(s: RelayState): boolean { return (s as { disposed: boolean }).disposed; }`. Это делает чтение прозрачным для лента и сохраняет валидную проверку.

**Применение:** любые поля состояния, мутируемые из внешнего scope (timer-callback, dispose-callback, web event), читать через функцию-обёртку с явной типовой обвязкой.

## [vscode] vscode.lm не в @types/vscode для engines.vscode ^1.80

**Контекст:** компиляция `aiMerge.ts` проходит, но lint выдаёт ~30 ошибок `no-unsafe-*` на `vscode.lm.selectChatModels` и `vscode.LanguageModelChatMessage`.

**Суть:** в `@types/vscode` соответствующего минимального engine `^1.80` API нет; рантайм его экспонирует на 1.90+. Решение — type-shim в файле использования: declare local `interface LmApi { ... }` + `getLm(): LmApi | null` через `vscode as unknown as VscodeWithLm`. Lint не трогает, рантайм работает на поддержанных версиях.

**Применение:** для feature-gated VS Code API из новых версий — типизировать локально, не поднимать минимальный `engines.vscode` ради типа (это отрезает аудиторию).

## [баг] Git stash drop без разрешения конфликта = потерянная работа

**Контекст:** при попытке временно отложить правки через `git stash` для baseline-сравнения, последующий `git stash pop` дал warning о LF/CRLF и stash остался в очереди (а не удалился). Я сделал `git stash drop` — получил «Already up to date» по part of the changes; на самом деле сложился частичный мёрж и часть правок ушла в потерянный объект.

**Суть:** `git stash drop` после неуспешного `git stash pop` уничтожает блок в reflog. Восстанавливать через `git fsck --lost-found` → `dangling commit` → `git stash apply <hash>`. Но если на этот момент в working dir уже есть конфликтующие изменения — нужно сначала их сохранить отдельным stash.

**Применение:** перед `git stash drop` ВСЕГДА проверять `git status` и фактически файлы (не только git status, который может показывать лишь часть). Лучше использовать `git stash apply` (без drop) до явного подтверждения что всё на месте. Альтернатива — коммит локально в throwaway-branch, потом `git checkout main` и работа.

## [баг] Edit обрезает большие файлы если не прочитан через Read

**Контекст:** при правке extension.ts (4400+ строк) и других крупных файлов файлы обрезались до частично прочитанного фрагмента.

**Суть:** инструмент `Edit` требует предварительного `Read` именно через инструмент `Read` — `bash cat` не засчитывается. `Read` без параметров читает максимум 2000 строк. Если после этого вызвать `Edit` — инструмент знает только прочитанный фрагмент и пишет усечённый файл. Итог: всё что было ниже окна чтения — уничтожается.

**Применение:** для файлов >1000 строк — не использовать `Edit` напрямую. Вместо этого: читать оригинал из git (`git show HEAD:path > /tmp/orig`), делать точечные `str.replace()` в Python-скрипте, писать результат целиком. Это атомарно и не зависит от размера файла.

## «Верхний ползунок» / «ползунок бегает» — май 2026

**Контекст:** пользователь жаловался что «верхний ползунок бегает» пока «нижний спинер остановился». Потребовалось несколько попыток чтобы понять о чём речь.

**Суть:** «верхний ползунок» = тонкая полоска прогресса в заголовке панели WORKSPACES (встроенный индикатор загрузки VSCode). Появляется автоматически когда `getChildren()` TreeDataProvider выполняет `await` на асинхронный вызов. «Нижний спинер» = иконка синхронизации в статус-баре (`statusBar.setSyncing(true/false)`). Это два разных индикатора с независимым жизненным циклом.

**Применение:** когда пользователь говорит про «ползунок» в контексте панели воркспейсов — это панельный индикатор загрузки, не статус-бар и не окно VS Code целиком.

## Inline-кнопки дерева недоступны во время загрузки — май 2026

**Контекст:** пользователь сообщил что «триточки на воркспейсе не работают» пока «ползунок бегает».

**Суть:** VSCode блокирует ВСЕ inline-кнопки во всей панели пока `getChildren()` ожидает async-результат. Один медленный сетевой вызов (например `listRemoteWorkspaceSummaries`) в `buildCloudSectionElements` замораживает кнопки на всех элементах — включая локальные воркспейсы у которых нет сетевых зависимостей.

**Применение:** любой `await` внутри `getChildren` → панель тормозит. Решение: stale-while-revalidate (возвращать кеш мгновенно, обновлять в фоне).

## rebuildManifestFromLocalState воссоздаёт удалённый воркспейс — май 2026

**Контекст:** баг — воркспейс удалённый на одной машине появлялся снова на другой.

**Суть:** когда manifest NOT_FOUND в `syncWorkspace()`, код вызывал `rebuildManifestFromLocalState()` который **заново загружал манифест на облако**. Это правильно при случайной потере манифеста, но неправильно при намеренном удалении другой машиной. Различие: если папка воркспейса на облаке пустая/отсутствует → намеренное удаление → авто-отвязка; если папка есть но манифест отсутствует → accidental loss → rebuild.

**Применение:** при любых изменениях в `syncWorkspace()` помнить об этом разграничении.

## $(sync~spin) в дереве НЕ блокирует кнопки — май 2026

**Контекст:** при добавлении loading-спиннера для remoteOffer элементов.

**Суть:** иконка `$(sync~spin)` на tree item — просто анимированная иконка, она НЕ вызывает панельный индикатор загрузки и НЕ блокирует кнопки. Блокировку вызывает только `await` в `getChildren`. Для блокировки кнопок на конкретном элементе нужно менять `contextValue` так, чтобы `when`-условия в package.json не срабатывали.

**Применение:** для loading-состояния элемента использовать отдельный contextValue (например `vscodeSync.remoteOfferLoading`), а не полагаться на иконку.

## TTL-кеш remote summaries: invalidate нужен явно — май 2026

**Контекст:** добавление кеша для `_fetchRemoteSummaries` в `WorkspacesTreeProvider`.

**Суть:** после операций attach/delete воркспейса кеш нужно сбрасывать явно через `invalidateRemoteCache()`, иначе секция «Доступные на облаке» покажет устаревший список до истечения TTL (8 сек). Обычный `refresh()` кеш НЕ сбрасывает — только обновляет UI из кеша.

**Применение:** везде где меняется состав воркспейсов на облаке — вызывать `workspacesTree.invalidateRemoteCache()` перед `refresh()`.

## [договорённость] Убрать «Co-authored-by: Cursor» из коммитов

**Контекст:** Cursor автоматически добавляет строку `Co-authored-by: Cursor <noreply@cursor.com>` в сообщения коммитов.

**Суть:** создать git hook `.git/hooks/commit-msg` с содержимым:

```bash
#!/bin/sh
sed -i '/Co-authored-by: Cursor/d' "$1"
```

Затем сделать исполняемым: `chmod +x .git/hooks/commit-msg`. Hook работает в Git Bash / MINGW на Windows. Файл находится в `.git/hooks/` (не коммитится), поэтому нужно создавать заново при клонировании репо.

**Применение:** при настройке нового клона репозитория или если строка снова появляется в коммитах.

## [архитектура] Паттерн `dir/` в `ignoreMatch` не исключает файлы внутри каталога

**Контекст:** рекурсивное добавление папки в sync фильтруется через те же правила, что и одиночный файл; проверяли ожидание «`foo/` = весь подкаталог».

**Суть:** флаг `directoryOnly` в парсере лишь отрезает суффикс `/` у шаблона; сопоставление идёт как с полным `posixRel` файла. Шаблон вроде `a/b/` становится `a/b` и матчит только путь ровно `a/b`, не `a/b/file.ts`. Чтобы исключить дерево, нужны шаблоны уровня `a/b/**` или маски по имени файла.

**Применение:** документация для пользователей и тесты на ignore при bulk-add; при доработке матчера — не смешивать с семантикой git без явного решения.

## [vscode] Пункт VSCodeSync для папки в Explorer: `when` без `resourceScheme`

**Контекст:** подменю с `resourceScheme == file && explorerResourceIsFolder` не показывалось при ПКМ по папке.

**Суть:** для **папки** в контексте Explorer надёжнее вешать команду с **`when": "explorerResourceIsFolder"`** и по возможности **прямой `command`**, а не единственный пункт во вложенном submenu. Сочетание с **`resourceScheme == file`** в отдельных сборках/конфигурациях может отсечь весь вклад.

**Применение:** новые вклады в `explorer/context` для каталогов; отладка — Developer: Inspect Context Keys на ПКМ по папке.

## [баг] EPERM при атомарной записи JSON на Windows

**Контекст:** ошибка `EPERM: operation not permitted, rename '…vscodesync.json.*.tmp' -> '…vscodesync.json'` при сохранении конфига воркспейса.

**Суть:** на Windows `rename` поверх **уже существующего** файла часто возвращает EPERM/EACCES/EBUSY, пока у файла есть открытый handle (редактор, file watcher, индексатор, антивирус).

**Применение:** несколько попыток `rename` с backoff; если после этого всё ещё блокировка — для обычных JSON-конфигов допустим fallback на прямой `writeFile` тем же содержимым. Для lock-файлов без fallback — только retries.

## [архитектура] If-Match на blob не заменяет 3-way перед push

**Контекст:** после правок на одной машине «домашняя» копия успела залить старое содержимое в облако.

**Суть:** успешный PUT с `If-Match: текущий etag` лишь означает «замени эту ревизию blob»; если в `_meta` уже зафиксирован **новый** канонический хэш (другая машина успела), а локально на диске **старая** версия, etag всё равно совпадает с текущим blob — сервер примет перезапись. До upload нужна та же **трёхсторонняя проверка**, что в `syncOneFile` (`detectChange` + опциональный pull); явные keep-mine / auto-resolve передают признак и обходят проверку.

**Применение:** любые точки входа в `pushFile` (save, commit, offline queue); при доработке блокировок файла — reconcile вызывать **вне** `runWithSyncFileLock(..., "push")`, иначе `pullFile` в том же pipeline приведёт к deadlock.
