# Changelog

All notable changes to **VSCodeSyncFiles** are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project follows a custom `major.minor.maintenance` scheme (each part 0–99,
no carry on 9). See `CLAUDE.md` for build versioning rules.

## [Unreleased]

## [1.6.1] — 2026-08-14

### 🐛 Исправления

- **Авто-пауза по git-ветке больше не зависит от облака.** Решение о паузе
  локальное, но принималось после получения авторизованного провайдера — и
  если провайдер недоступен (не залогинены, нет сети, форк редактора со своим
  хранилищем секретов), функция молча не срабатывала. Теперь пауза
  применяется до любых обращений к облаку, прямой записью в локальный конфиг;
  пересчёт статусов при авто-возобновлении стал best-effort и догоняет при
  первом обычном проходе.
- **Проход по ветке объясняет своё бездействие.** Каждый ранний выход — нет
  доверия к папке, выключен `gitBranchAutoSync`, `autoSyncMode: off`, нет
  подключённых воркспейсов, не определилась ветка, нет провайдера — пишет
  строку в канал VSCodeSync (уровень `verbose`). Раньше симптом читался как
  «расширение ничего не делает», без следа причины.

### ♻️ Внутреннее

- Запись плана паузы в конфиг вынесена в чистую функцию
  `applyBranchPausePlanToConfig` и покрыта тестами; добавлен гейт на порядок
  вызовов — пауза обязана решаться раньше обращения к провайдеру.

## [1.6.0] — 2026-08-13

### ✨ Новое

- **Пауза воркспейса, пригодная для прыжков по git-веткам.** Приостановленный
  воркспейс теперь не только не двигает файлы, но и не обновляет статусы:
  `git checkout` больше не заливает дерево строками «pending push» там, где вы
  попросили тишины. Такие строки остаются видны в панели «Расхождения», но не
  попадают в счётчик, статус-бар и уведомления, а в дереве подписаны
  «⏸ статус заморожен» — это снимок, а не текущее состояние.
- **Пакетная пауза.** Команды «Приостановить / Возобновить воркспейсы (выбор)»
  — список с галочками, по умолчанию отмечены все, доступны из заголовка
  панели «Воркспейсы». Возобновление сразу пересчитывает статусы, поэтому
  дерево не показывает состояние «до паузы».
- **Авто-пауза по смене git-ветки для воркспейсов без привязки.** Настройка
  `vscodesync.git.autoSuspendUnbound` (по умолчанию выключена): ушли с ветки,
  на которой работали, — воркспейс уходит в паузу; вернулись — сам
  возобновляется с пересчётом статусов. Паузу, поставленную руками,
  автоматика не снимает; на detached HEAD не срабатывает. Воркспейсы с
  привязкой `gitBranch` по-прежнему следуют своей ветке.

### 🐛 Исправления

- **«Обновить» в панели «Расхождения» обновляет и дерево.** Кнопка пересчитывала
  статусы, но перерисовывала только панель: слева оставались устаревшие
  «pending push», справа — уже верные цифры.
- **Пустой центр панели объясняет себя.** Под фильтром без совпадений теперь
  сказано, сколько строк даёт «Все» — пустота при непустой шапке читалась как
  поломка.
- **Удаление воркспейса вместе с локальными файлами учитывает привязки путей.**
  На машинах с `pathMapping` или привязанными файлами удаление промахивалось
  мимо реальных путей молча, а итог называл заниженное число файлов.
- **«Разморозить» больше не синхронизирует без спроса.** Снятие Freeze
  безусловно гнало полный sync — данные ехали в обе стороны с кнопки, которая
  обещала только снять заморозку. Теперь тот же предпросмотр и подтверждение,
  что у «Разархивировать».
- **Реакция на смену ветки работает без расширения Git.** `.git/HEAD` читается
  напрямую, когда API расширения недоступно; раньше вся политика веток на таких
  установках была недостижима.

### ♻️ Внутреннее

- Команды получили категорию **VibeSync**: префикс «VSCodeSync: » убран из 182
  заголовков, палитра печатает категорию сама, а в контекстных меню остаётся
  короткое название. Восемь команд, добавленных без префикса, снова находятся
  в палитре по имени расширения. Добавлен тест-гейт, чтобы префикс не вернулся.

## [1.5.0] — 2026-08-13

### ✨ Новое

- **Только расхождения.** Кнопка-фильтр в заголовке панели «Воркспейсы»
  оставляет в дереве лишь файлы, требующие действия: конфликт, не отправлено,
  есть новее в облаке, нет на диске. Папки без таких файлов исчезают вместе с
  ними, выбор запоминается между запусками. На сотне отслеживаемых файлов это
  разница между «искать глазами» и «увидеть сразу»; если расхождений нет, об
  этом говорится прямо — пустое дерево не выглядит поломкой.
- **Пакетные действия по выделению.** В дереве можно выделить несколько файлов
  (Ctrl/Shift-клик) и отправить или скачать их одной командой: один вопрос о
  размещении на весь набор вместо N, один итог «сделано N из M».
- **Действия прямо в строке панели «Расхождения».** «↓ Скачать» и
  «↑ Отправить» рядом со «Сравнить» — раньше для одного файла приходилось
  отмечать чекбокс и идти к массовой кнопке. Обратное направление доступно
  тоже, но спрашивает подтверждение: это единственное место, где один клик
  затирает более свежую сторону. Признак направления переоформлен так, чтобы
  его нельзя было принять за кнопку.
- **Выборочная синхронизация.** Настройка `vscodesync.selectiveSync.mode`
  решает, как во время синхронизации читаются ваши паттерны исключений:
  как раньше (только при добавлении и ручной отправке), «не синхронизировать
  совпавшее» или «синхронизировать только совпавшее». Перед переключением
  показывается поимённо, что перестанет и что начнёт синхронизироваться;
  массовая остановка требует отдельного подтверждения. Отфильтрованный файл
  остаётся на диске и в облаке — он просто перестаёт синхронизироваться на
  этой машине.
- **Слияние по участкам.** Трёхпанельный вид (общая база · ваша версия ·
  облачная) с выбором источника для каждого конфликтного участка — вместо
  решения «весь файл мой» или «весь файл чужой». Чистые участки сливаются
  сами; ничего не записывается, пока вы не нажмёте «Применить».
- **Проверка резервной копии.** Команда и периодическая фоновая проверка
  отвечают на вопрос, которого раньше никто не задавал: «из копии во втором
  облаке реально можно восстановиться?». Сравниваются составы и версии
  записей, отчёт перечисляет отставшие, отсутствующие и лишние. Только чтение:
  расхождения показываются, ничего не копируется и не чинится само.
- **Панель квоты провайдера.** Сколько обращений к API израсходовано за
  скользящие сутки и как это соотносится с суточным лимитом провайдера —
  ответ на «скоро ли меня начнут ограничивать».
- **Онбординг рассказывает о разной структуре папок.** Новый шаг «Структура
  папок может отличаться» встал сразу после «Добавьте файл» — там, где вопрос
  и возникает. Пустая панель воркспейсов и контекстная подсказка при файлах
  «нет на диске» тоже ведут к привязке папки, а не к массовому скачиванию.

### 🐛 Исправления

- Контекстное меню VSCodeSync в проводнике зависело от файла, открытого **в
  редакторе**, а не от того, по которому щёлкнули: открытый отслеживаемый файл
  прятал «Привязать…» и «Добавить…» у любого файла в дереве проводника, а
  «Отправить / Скачать / Сравнить» показывал у неотслеживаемых.
- Обёртка учёта запросов теряла серверный перенос файлов, безвозвратное
  удаление и ссылку на веб-интерфейс провайдера: подключение панели квоты
  молча вернуло бы переезды путей к полной перекачке.
- Команды «Привязать папку…» и «Скачать папку» показывались в палитре, где
  ничего не делали — они работают только на узле папки в дереве.

### ♻️ Внутреннее

- Удалены `selectiveSyncFilter` и `selectiveSyncTemplate`: их замысел
  реализован поверх существующих правил исключений, а второй диалект глобов
  рядом с рабочим однажды дал бы два разных ответа на один вопрос.
- Рефакторинг ядра (`syncEngine` → оркестратор) отложен отдельным заходом;
  потолок держится выносами по ходу фич.

## [1.4.1] — 2026-08-13

> Выпускается вместе с содержимым 1.4.0 — тот сборкой остался внутри разработки
> и отдельным релизом не публиковался.

### ✨ Новое

- **Дерево показывает структуру воркспейса.** Файлы сгруппированы так, как они
  лежат в самом воркспейсе, — по этой структуре другие машины раскладывают
  файлы при засеве. Раньше дерево по умолчанию группировало по локальному
  размещению, и правка облачных путей выглядела как «ничего не произошло»:
  байты при переезде не двигаются, двигаются только пути в облаке. Признак ⇄
  на узле показывает, где файл лежит на этой машине, когда размещения
  разошлись. Кнопка «структура воркспейса ⇄ как лежит у меня» переключает
  пространство и запоминает выбор между запусками.

### 🐛 Исправления

- Настройка `vscodesync.tree.groupFilesByFolder: false` не давала плоский
  список в режиме облачной структуры — дерево строилось всё равно.

## [1.4.0] — 2026-08-12

### ✨ Новое

- **Вытащить из папки одним действием.** «Вытащить из папки (на уровень выше)»
  на файле или папке дерева поднимает узел из вложенности: имя сохраняется,
  родитель уходит, дочерние пути перестраиваются; повторный вызов доводит до
  корня. Это переезд облачной структуры — новые пути засеются на других
  машинах. Перетаскивание на узел воркспейса (в корень) тоже работает.
- **«Переместить у меня» — и автору переезда.** После собственной правки путей
  машина получает то же предложение разложить свои файлы по новой структуре
  (батч с прогрессом и отменой), что и остальные машины при реплее — раньше
  локальное дерево «не реагировало» на свой же переезд.
- **История следует за файлом сквозь переименования.** Прошлые версии,
  сделанные под прежними облачными именами, остаются в списке истории и
  открываются как раньше; нативная шкала Timeline VS Code показывает события
  файла по его идентичности, а не по текущему пути — след больше не обрывается
  на переименовании.
- **Сборка мусора в облаке.** Health Check по кнопке проверяет воркспейсы на
  осиротевшие объекты (блобы и историю под мёртвыми ключами, лишние строки
  `_meta` — след прерванных переездов и проигранных гонок) и по подтверждению
  отправляет их в корзину провайдера с отчётом «освобождено X МБ». Ничего не
  удаляется мимо корзины; объекты, чей возраст нельзя установить, не трогаются
  и перечисляются отдельно.
- **Ремонт задвоенной идентичности — кнопкой.** Дубликаты linkId (след гонки
  привязки с переименованием) чинятся из Health Check одним нажатием:
  выживает новейший носитель, привязки машин сливаются. Еженедельная
  авто-проверка теперь предупреждает о таких дублях.

### 🚀 Производительность

- **Переезды путей без перекачки содержимого.** Переименования и переносы в
  облаке выполняются серверным перемещением провайдера — во всех четырёх
  (OneDrive, Google Drive, Dropbox, Яндекс.Диск). Папка на сотни файлов
  переезжает за секунды вместо полного скачивания и заливки; история файлов
  переезжает так же. Полная перекачка остаётся только там, где меняется форма
  хранения (категория текст↔бинарь, gzip).

### 🐛 Исправления

- Быстрый путь серверного переноса был недостижим: обёртка провайдера не
  пробрасывала опциональный метод — каждый «нативный» переезд молча
  деградировал в полную перекачку.
- Time-Travel слайдер для привязанного файла (локальное имя отличается от
  облачного) говорил «нет записей» — листался каталог локального имени вместо
  облачного ключа.

### ♻️ Внутреннее

- Потолок движка удержан выносами: health-операции манифеста, читатели
  блобов/истории, GC и прунинг трекинга — отдельные модули с тестами.
- Тесты провайдеров: нативный move покрыт fake-fetch тестами всех четырёх
  провайдеров + проброс через очередь и фолбэк ядра при ошибке move.

## [1.3.0] — 2026-08-12

### ✨ Новое

- **Правка путей воркспейса.** Структура в облаке редактируется как своя:
  канонический путь любого узла — файла, папки, целого корня — меняется прямо
  из дерева, и дочерние пути перестраиваются. Идентичность файлов и привязки
  машин переживают любые переезды; локальные файлы не перемещаются ни на одной
  машине — физический перенос остаётся явным действием по клику. Три способа
  правки: команды на узлах («Изменить путь в облаке…», «Переименовать облачную
  папку…»), перетаскивание файла или папки в другую папку того же воркспейса
  и массовый редактор («Редактировать пути воркспейса…» — буфер «строка =
  файл», мультикурсор и regex-замены, один батч с одним подтверждением).
  Перед применением — превью «было → станет» с коллизиями и предупреждениями
  (различие только в регистре; смена категории текст↔бинарь). Последнее
  переименование отменяется одной командой; прерванный на полпути перенос
  предлагает «Возобновить» — в том числе после перезапуска VS Code.
- **Канонический режим дерева.** Кнопка ⇄ на панели переключает дерево между
  локальным размещением и структурой облака — правка путей видна в том
  пространстве, где живёт.
- **Засев по путям воркспейса.** Залили файлы с одной машины, поправили пути в
  облачном дереве, подключили вторую — вопрос «куда положить папку» задаётся
  до скачивания, и файлы ложатся по отредактированной структуре.
- **Понятные уведомления о чужих переездах.** Вместо потока тостов — одно
  уведомление на операцию («папка X → Y, N файлов; локальные файлы не
  тронуты») с кнопкой «Переместить у меня»: раскладывает файлы по новой
  структуре с прогрессом и отменой. Конкурирующие переименования с двух машин
  сходятся папкой целиком, проигравшая правка сообщает об этом явно.
- **Русский — базовый язык интерфейса.** Команды и настройки показываются
  по-русски при любом языке редактора; английский остаётся для локали en
  (`package.nls.en.json`).

### 🐛 Исправления

- Переименование файла в путь, освободившийся после удаления, рождало «мёртвую»
  запись — файл выглядел удалённым сразу после переезда.
- При смене расширения в переименовании облачный хэш переносился без пересчёта —
  файл навсегда выглядел разошедшимся (текст и бинарь хэшируются по-разному).
- Старый блоб удалялся до записи манифеста — обрыв сети посреди переименования
  оставлял манифест, указывающий на удалённые байты. Теперь удаление — строго
  последний шаг, обрыв безопасен и возобновляем.
- История версий файла терялась при переименовании — теперь следует за файлом.
- Восстановление манифеста после потери в облаке проигрывало слияние старым
  копиям (версии начинались с 1) — теперь стартует выше всего виденного.
- Ремонт задвоенной идентичности файла существовал, но не был подключён —
  теперь срабатывает автоматически при слиянии конкурентных правок.
- Массовое переименование папки ловило ложную модалку «массовое удаление» и
  предупреждение «файлы будут потеряны» — переезд больше не считается
  удалением.
- Отвязка файла не сбрасывала привязку в облаке — повторный засев мог лечь по
  устаревшему пути.
- Семь файловых команд показывались в контекстном меню папок дерева.

### ♻️ Внутреннее

- Property-тесты сходимости переездов: 50 сидов случайных конкурирующих батчей
  × все порядки слияния (включая вырожденное равенство версий) → одна живая
  структура на всех репликах.
- Ядро переезда вынесено в чистые модули (`canonicalRename`,
  `planCanonicalRename`, `io/canonicalRelocation`); `renameTrackedFile`
  переведён на общую машинерию; потолок движка соблюдён.
- Задел под серверный перенос блобов без перекачки: опциональный
  `provider.moveFile` + быстрый путь (реальные провайдеры — follow-up).

## [1.2.0] — 2026-08-11

### ✨ Новое

- **Дерево папок в панели вместо сплошного списка.** Полсотни файлов больше не
  лежат портянкой: отслеживаемое показывается той же иерархией, в которой вы
  работаете, цепочки одиночных папок схлопываются в одну строку, а признак
  привязки (`⇄ облачный/путь`) стоит один раз на папке, а не на каждом файле.
  У папки появились свои действия — «Скачать папку» и «Привязать папку к
  другому локальному пути…». Плоский список остаётся в настройке
  `vscodesync.tree.groupFilesByFolder`.
- **Отправка папки с выбором пути в облаке.** При добавлении папки расширение
  спрашивает, каким путём она должна лежать в облаке, и предлагает срезать
  начало локального пути: дома `src/SEMD272/jscore/` уезжает как `jscore/` —
  и на машине, где префикса `src/SEMD272/` нет, файлы лягут ровно по своим
  местам. Обрезанная часть запоминается правилом этой машины, поэтому файлы,
  добавленные в ту же папку позже, следуют тому же отображению.
- **Приём облачной папки в своё место.** При подключении воркспейса каждая
  верхнеуровневая папка спрашивает: «Взять как есть» или «Положить в свою
  папку…» — так `php/**` из облака становится `promed/**` у вас. Целевой папки
  может ещё не быть: правило решает, куда попадут будущие файлы, а сама папка
  создастся при скачивании. Перед записью показывается предпросмотр «облако →
  сюда», сколько структуры совпало и что уже лежит на месте — существующие
  файлы не перезаписываются молча, а расходятся в панель «Расхождения».
- **Выбор папок для синхронизации на этой машине.** Машина может нести не весь
  воркспейс: команда `VSCodeSync: Выбрать папки для синхронизации на этой
  машине…` оставляет нужные облачные папки, остальные перестают отслеживаться,
  не числятся отсутствующими и не показываются в дереве. Выбор локальный — в
  облаке и на других машинах остаётся всё.

### ♻️ Внутреннее

- Четыре почти одинаковых метода записи полей манифеста (заметка, теги, общие
  правила исключений, git-ветка) сведены к одному; логика привязки папок
  вынесена из движка в отдельный модуль.

## [1.1.0] — 2026-08-11

### ✨ Новое

- **Привязки (Link Bindings): структура папок не обязана совпадать между
  машинами.** У файла в облаке появилась стабильная идентичность и
  «линковочное имя», а каждая машина может держать его в своём месте и под
  своим именем. Привязка — чистые метаданные: содержимое при ней не
  перемещается никогда.
  - *Привязка файла* — «VSCodeSync: Привязать локальный файл к облачной
    записи»: существующий локальный файл связывается с облачной записью;
    при совпадении содержимого файлы сразу синхронны, при различии —
    штатное расхождение в панели.
  - *Привязка папки* — целая папка с одинаковой структурой внутри может
    называться по-разному (на работе `promed/`, дома `php/`). Правило
    действует и на будущие файлы: новое из облака попадает в вашу папку,
    добавленное из неё — под облачный префикс.
  - *Выбор размещения при скачивании* — файл, которого ещё нет на машине,
    можно положить по записанному пути, в свои папку и имя или привязать к
    уже существующему файлу без скачивания; при массовом скачивании — один
    вопрос на весь набор.
  - *Дедуп при добавлении* — если файл, похоже, уже есть в облаке (по
    содержимому или имени), расширение предлагает привязаться к существующей
    записи, а не плодить вторую.
  - *Переносы без сюрпризов* — переименование непривязанного файла
    спрашивает «в облаке для всех» или «только на этой машине»; чужое
    облачное переименование никогда не двигает локальные байты — перенос
    только по явному клику в уведомлении.
  - *Честный статус «нет на диске»* — отслеживаемый, но отсутствующий файл
    больше не выглядит синхронизированным: свой значок в дереве и Explorer,
    строка «есть в облаке, нет локально» в панели с действием «Привязать…».
- **Мастер первого запуска и walkthrough описаны в каталоге возможностей**,
  битые видеоплееры «Начала работы» заменены полноценными текстовыми шагами
  (разрешение конфликта, Time-Travel слайдер).

## [1.0.0] — 2026-08-06

**Главный принцип 1.0.0: данные двигает пользователь.** Расширение больше не
отправляет и не скачивает файлы само — автоматика считает расхождения и
показывает их, а отправка, скачивание и разрешение конфликтов происходят по
явной команде. Этот выпуск закрывает сквозной аудит: 61 дефект в семи разделах,
от операций, разрушающих данные в один клик, до слоёв ядра.

> ⚠️ **Требуется действие: снапшоты, созданные до 1.0.0, не шифровались.**
> Обновление не исправляет уже загруженные снапшоты. Если в воркспейсе были
> секреты (`.env`, ключи, токены) — удалите старые снапшоты из облака и смените
> сами секреты. Подробности — в первом пункте раздела «Безопасность».

### 🔒 Безопасность

- **Снапшоты уходили в облако открытым текстом.** При включённом
  `vscodesync.encryption` движок шифровал блобы файлов, а снапшот клал рядом
  полную читаемую копию воркспейса — причём три из восьми точек вызова
  автоматические (перед merge, перед ротацией ключа, по расписанию). Контекст
  шифрования стал обязательным параметром; в мету добавлен маркер формата, так
  что старые снапшоты восстанавливаются, а новые без ключа — нет. Если ключ
  недоступен, снапшот **не создаётся** вместо записи открытым текстом.
  **Снапшоты, снятые до 1.0.0, правкой не исправляются** — при секретах в
  воркспейсе их следует удалить и пересоздать.
- **Вход в Яндекс.Диск: implicit flow и приём токена без проверки.** Поток
  отдавал токен во фрагменте URL, поэтому требовался HTML-шим, POST-ящий его на
  локальный сервер; тот принимал что угодно — ни `state`, ни `Origin`, ни
  `Content-Type` — на фиксированном порту. Cross-origin form-POST мог подсунуть
  чужой токен, и файлы поехали бы в чужой Диск. Поток переведён на
  authorization code + PKCE, шим удалён целиком.
- **Приём файлов по P2P — за настройкой и через staging.** Пир больше не
  пишет в рабочее дерево: `vscodesync.p2p.acceptIncomingFiles` выключена по
  умолчанию, входящие ждут в `.vscode/vscodesync-incoming/` до вашего
  «Применить / Сравнить / Отклонить».

### 🐛 Исправления

- **Операции, разрушающие данные в один клик.** AI-слияние писало ответ модели
  поверх файла и сразу пушило — теперь дифф, подтверждение, бэкап, а отправка в
  облако отдельным вопросом. «Восстановить файл» после удаления одного файла
  делало force-pull всего воркспейса мимо `detectChange` — теперь скачивается
  ровно удалённый файл. Quick Transfer молча перезаписывал существующий файл —
  теперь «Перезаписать (с бэкапом) / Сохранить рядом / Отмена», а облачный
  пакет удаляется только после успешной записи.
- **«Оставить моё» могло похоронить чужую версию.** Запоминается облачный хэш
  на момент отметки конфликта; если облако ушло вперёд, расширение
  предупреждает и предлагает сравнить вместо тихой перезаписи.
- **Три параллельные реализации разрешения конфликтов сведены к одной.**
  Команда «Разрешить конфликт — Оставить моё» лишь снимала флаг локально и
  советовала «при необходимости выполнить Push»: пользователь выбирал её вместо
  правильной (заголовки почти неотличимы), файл в облако не уходил, вторая
  машина оставалась со старой версией. Команда удалена. Вторая копия писала
  `syncStatus = "ok"` на диск **до** pull — при сбое сети конфликт исчезал
  навсегда, а расходящаяся локальная версия затирала облачную при следующем
  push.
- **Статус файла «плавал» между проверками.** Решение push/pull/conflict
  принималось в четырёх местах, и три из них не учитывали случай «файл правили
  и вернули к исходному»: панель показывала «↓1», Pull ничего не менял,
  следующая проверка снова рисовала «↓1».
- **Просроченный токен выглядел как «нет сети».** Ошибки провайдеров
  классифицировались в 48 местах, из которых 46 отвечали «сетевая ошибка»:
  отозванный токен уходил в бесконечный ретрай вместо предложения войти заново.
  Введён единый классификатор; добавлен принудительный refresh по 401 —
  истечение по времени не видит токен, отозванный на сервере.
- **Google Drive: чтение создавало папки.** `listFolder` при промахе создавал
  структуру в вашем Drive — а проверка связи вызывает его каждые 30 секунд.
  Чтение и создание разделены. Одноимённые файлы (Drive их допускает)
  разрешаются детерминированно, а не «первым попавшимся».
- **Удаление стало обратимым.** Google Drive и Яндекс стирали файл
  безвозвратно, две другие службы — в корзину. Теперь корзина везде;
  безвозвратное удаление — отдельная операция по прямой команде.
- **Проверка целостности `providerHashVerify` ломала push на OneDrive.** Она
  сравнивала непрозрачный `ETag` (у Graph это `{GUID},N`, у Dropbox — `rev`) с
  хэшем содержимого, поэтому каждая успешная заливка завершалась ошибкой
  целостности. Появилось отдельное поле дайджеста, заполняемое из того, что API
  определяет как хэш.
- **Файлы больше ~150 МБ не заливались в Dropbox никогда** — подключена
  сессионная заливка. У OneDrive чанковая заливка шла мимо общей обработки:
  троттлинг падал без учёта `Retry-After`, а любой сбой перезаливал файл с
  нуля — теперь возобновление с нужного байта.
- **`createFolder` у OneDrive был пустой заглушкой**, а у Dropbox отсутствовал
  «Открыть в облаке» — обе дырки закрыты.

### ✨ Новое

- **Отмена работает.** У «Отправить всё», «Скачать всё» и «Синхронизировать
  воркспейс» появилась кнопка «Отмена», которая действительно останавливает
  операцию: сигнал доходит до запроса в сети. Раньше один запрос мог занимать
  до ~16 минут (три попытки по 120 с плюс `Retry-After` до 300 с), и ждать
  оставалось только его. `Retry-After` теперь ограничен минутой.
- **Выбор способа входа.** «VSCodeSync: Войти в облако» — одна команда вместо
  девяти: браузер первым (редирект возвращается на `127.0.0.1`, вводить нечего)
  и код устройства вторым, для SSH и контейнеров. Доступно для всех четырёх
  служб.
- **«VSCodeSync: Открыть панель…»** — одна команда вместо шести отдельных.
- **Панель настроек показывает все настройки.** Раньше она знала 67 ключей из
  92, а два из показанных были удалены из схемы: VS Code отклонял запись, а
  панель рапортовала «Сохранено». Каталог теперь генерируется из манифеста.
- **Меню редактора учитывает состояние файла:** «Добавить в синхронизацию» —
  только для неотслеживаемых, push/pull/сравнение — только для отслеживаемых,
  «Оставить моё / Взять их» — только при конфликте.

## [0.8.0] — 2026-05-21

**Audit-pass релиз. Pull rollback гонка закрыта; UX-фичи вокруг ручного

### 🐛 Исправления

- **Pull rollback race.** После ручного Pull статусы файлов мгновенно
  возвращались в ✓, но через 30–60 секунд откатывались обратно в
  `cloud_newer` / `pending_push`. Это происходило при работе с одним

    локальный статус принудительно становился `cloud_newer` — даже
    если хеш диска уже совпадал с облаком. Soft lock теперь остаётся
    **UI-индикацией** через `file.editingBy/editingByName`, а реальный
    статус вычисляется через `checkOneFileStatus` (3-way compare).
  - **Окно гонки в `pullFile`.** Порядок инвертирован: сначала

    закрывает окно между «cfg уже OK» и «meta на cloud ещё старая», в

  - **`checkOneFileStatus` missing `consensusLagsLocally` rule.** В

## [0.7.0] — 2026-05-21

**Крупный релиз. Содержит breaking change в поведении автосинхронизации.**

### ⚠ Breaking

- **`vscodesync.autoSyncMode` по умолчанию = `check-only`.** Раньше любое
  сохранение файла (`onSave`), открытие (`onOpen`) и фокус окна (`onFocus`)
  автоматически дёргали push/pull. Это создавало «гонку» при работе с одним
  workspace на нескольких машинах одновременно: дома сохранил → на работе
  откатилось → дома снова правишь → бесконечный цикл. Новый дефолт
  `check-only` оставляет автоматику только для **обновления статусов**
  (`pending_push` / `cloud_newer` / `conflict` подсвечиваются в дереве),
  но **push и pull выполняются только вручную**. Восстановить старое
  поведение: `vscodesync.autoSyncMode = full` или команда
  `VSCodeSync: Auto-sync mode → full`.

### ✨ Новое

- **`autoSyncMode`** — три режима: `off` (без автоматики), `check-only`
  (только подсветка статусов, default), `full` (историческое поведение).
- **Параллельная синхронизация** — `sync.concurrency` (default 4) для файлов
  внутри workspace и `sync.workspaceConcurrency` (default 2) для workspace'ов.
  Раньше один файл за раз — на больших workspace'ах ускорение до 4×.
- **Adaptive concurrency** — параллелизм автоматически снижается при
  низком заряде батареи, высокой загрузке RAM, или 429/503 от провайдера.
- **Connectivity probe + status bar widget** — иконка online/degraded/offline
  на статус-баре. При offline auto-sync тихо приостанавливается (без
  заваливания Activity Feed ошибками).
- **Sync profiler** — `VSCodeSync: Профиль синка` показывает топ-15
  самых медленных файлов с разбивкой hash/network/verify ms. Opt-in через
  `vscodesync.diagnostics.profileSync`.
- **`vscodesync://` URI scheme** — deep-links для workspace / file / command.
  Команда `VSCodeSync: Копировать share-ссылку` копирует ссылку в clipboard.
- **Invite-ссылки** — `VSCodeSync: Сгенерировать invite-ссылку для коллеги`
  (TTL 24h/7d/30d/без срока) + `VSCodeSync: Подключиться по invite-ссылке`.
- **Conflict — keep both** — третий путь разрешения помимо keep-mine /
  take-theirs: облачная версия сохраняется как `<name>.conflict-<machine>-<ts>`
  рядом, локальная остаётся как pending push.
- **Repair cloud manifest** — `VSCodeSync: Восстановить облачный манифест...`

### 🚀 Производительность
